Step 5 of 6 in INSTALL.md. Two independent parts. Do part A, checkpoint it, then part B. If part B fails, part A still counts and the install can still complete (see part B step 5).

Mac users: Part A applies to you in full. Part B (File Save Log) is Windows-only in this version. If my main computer is a Mac, skip Part B entirely: do not run the pre-install check, do not walk me through the manual checks in Part B step 1c as though my machine had failed them, and record File Save Log as skipped because my computer is a Mac, not as parked after a failure. Everything else in this kit works on macOS. Mac support for File Save Log is planned for a later version.

## Part B: File Save Log

   a. Ask me for the report from the pre-install check in INSTALL.md step 5. If I have not run it, walk me through running preinstall/Check-FileSaveLogRequirements.ps1 now, using the steps in INSTALL.md, and wait for the report before going any further.
   b. Read the report and act on it exactly: any FAIL line means we fix that item and I rerun the diagnostic, or we park this module per step 6, before any part of it is installed. A WARN line means we proceed, but we build the setup around it (for example, using the fallback windowless launch the report names). Use the report's exact paths and versions (the PowerShell 7 path, my folder paths, my log destination) in setup. Do not re-ask what the report already answers, and never copy a path from an example or another machine. If the PowerShell 7 line is a FAIL, the fix is to install PowerShell 7 from Microsoft (the free MSI or the Microsoft Store app), reopen the terminal, and run the diagnostic again.
   c. If I cannot run the diagnostic script at all, treat that as a warning sign in itself, and fall back to checking these by hand with me, reporting each in plain language: this computer is Windows and I can create a scheduled task under my own account (ask me whether the machine is managed by an employer or school; their policies may block parts of this, and we may need IT approval or we park); PowerShell 7 or later is installed, with its real path resolved on this machine (if it is missing, install PowerShell 7 from Microsoft, the free MSI or the Microsoft Store app, reopen the terminal, and resolve the path again); the windowless launch works here, proven by a small live test using the wrapper pattern in spec/FILE-SAVE-LOG.md section 2c, with the conhost.exe --headless fallback on Windows 11 if script host is blocked, and parking on Windows 10 if it is blocked there; my security software is not blocking that launch pattern (if it prompts, I decide whether to allow it). Also tell me, while you check: the wrapper uses VBScript, which Microsoft has deprecated and which is an optional feature in newer Windows versions, so a future machine may need the fallback.

2. Run the module interview from spec/INTERVIEW.md: folders that matter on my main computer, folders my own tools work in that should be excluded for me, the shipped exclusions read out loud, whether the full log lives in Drive or as a local file, the privacy notice, and the expectations list. Also offer me the shipped optional exclusion groups (extra backup files, build output folders, Snagit working files, screenshot folders) and the two settings: how many saves the panel shows (default 40) and how many months of log to keep (default 12). Record every answer; my choices on the optional groups and the settings are written into my user file in step 3, never into the defaults file. Where the diagnostic report already answered a question, confirm it with me instead of asking from scratch.

3. Set up the scanner and the aggregator per spec/FILE-SAVE-LOG.md, with these rules stated so there is no ambiguity:
   a. Scanner on my computer for the folders I chose, and no others, on this one computer only. Aggregator job every 15 minutes in my Muse. Preset exclusions on, plus my own folders from the interview. Dismiss and Hide always available on the panel. The pinned full-log entry in the File Saves History panel pointing at my log location. The panel shows the most recent saves up to my panel-size setting (default 40), and the master log rolls into an archive after my retention setting (default 12 months).
   a2. The exclusion rules are config-driven, in two JSON files placed in the scanner's folder. Install FileSaveLog-Excludes.json (the shipped defaults) exactly as it ships, and create my personal file, FileSaveLog-Excludes.user.json, by copying FileSaveLog-Excludes.user.template.json and filling its selfPaths with the scanner's install folder, so the scanner never logs its own files. My own rules from the interview (folders to keep out of the log entirely, folders to hide from the panel only) go in my user file, never in the defaults file, because updates replace the defaults file and never touch my user file. Python is not needed on my computer for this module, except for the optional explain.py check, which I can run myself only if I have Python 3 (or I can ask you, and you run it against my config).
   b. The scanner records metadata only: file name, full path, folder, save time, size, new or updated. It must never open, read, or copy a watched file, because reading a cloud placeholder file can force that file to download.
   c. Windowless launch, per spec section 2c, with no substitutes: the scheduled task action is the wscript.exe VBScript wrapper, never a direct PowerShell launch, because -WindowStyle Hidden still flashes and can be ignored; the task's own "Hidden" checkbox does not count, it hides the task in a list, not its window; and never set the task to "run whether the user is logged on or not", because outside my logged on session my cloud drives may not be mounted and scanner output can silently stop arriving.
   d. The task runs as me, interactive logon, limited level. It does not need admin rights and it cannot see other users' files; do not widen that.
   e. Resolve the real paths on this machine and put them in the config: the pwsh.exe path from the diagnostic report or step 1, each watched folder, the state file location, and the log destination, including the actual drive letter or OneDrive or Drive folder my sync app uses, confirmed running and mounted in this session. Before the first real cycle, check that every watched folder can be read and that the state location and the log destination can be written. The diagnostic's folder checks count for the folders it tested; check any additional folder the same way.
   f. Install the computer-side piece with the kit's ONE installer, filesave-log/Install-FileSaveLog.ps1. Run it from inside a PowerShell 7 session, in the kit's filesave-log folder, with the call operator and the diagnostic report's paths and my interview answers as its parameters, in this form: & '.\Install-FileSaveLog.ps1' -InstallDir '<install folder>' -Roots '<path>|<area>','<path>|<area>' -OutboxPath '<outbox folder>' -PwshPath '<pwsh.exe path>' (the same call also works through pwsh -Command). Do not launch it in the pwsh -File form: under -File, a comma separated list like the -Roots list can bind to the wrong parameter, so a watched folder can land in the wrong setting without any error showing. There is no second installer and no add-on: the one installer installs or refreshes the scanner, generates the windowless-launch wrapper with this machine's real paths, writes the excludes files and a fresh config, and registers the scheduled task (FileSaveLog-Scan at logon and every 15 minutes). Read its summary back to me component by component. The installer is idempotent, and its script decisions are: identical content is already current; when the installed scanner and the packaged copy both carry a $ScriptVersion marker, the higher marker wins and an installed scanner newer than the package is kept untouched (the summary says "kept (installed is newer)"); an installed scanner with NO marker is legacy, so the installer backs it up, replaces it, and warns, whatever its file date says. Re-running the installer on an up-to-date install changes nothing and reports every component already current, preserved, or registered. My FileSaveLog-Excludes.user.json and my config.json, once they exist, are preserved exactly; only the shipped defaults file is refreshed. If any component reports FAILED, treat it like any other failed check in this step: one troubleshooting pass, then park the module per step 6.
