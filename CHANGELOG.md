# Changelog

## 0.3.2 (pilot) - 2026-11-10

A catch-up batch that brings the kit in line with the reference board's latest behavior: the panel entry control is now called Details, dialogs across the board close one unified way with a "Changes will be lost" warning on editors, the brief's buttons sit slim at the right end of their row, a brief says nothing about screening when nothing was screened, briefs stack newest first within each day, the File Save Log installer refuses an invalid task name before it touches anything, and the specs now document a field quirk of the board's item-create action together with the write pattern that works around it.

Getting this version: on the release page, download only MyCommandCenter-Kit-v0.3.2-pilot.zip, ignore the Source code entries. Upgrading from v0.3.1, v0.3.0, v0.2.0, or v0.1.5: do not reinstall. Use prompts/upgrade.md from this kit, which upgrades your board in place and keeps all your data; it diagnoses first, backs up, and asks at each data-changing step.

Known limitations, stated plainly:

- The installer's new -TaskName validation (below) was rehearsed by Claude Code on Lenovo1 on 2026-11-10, in a sandbox with the live install untouched. Every invalid name tried (empty, whitespace only, and names containing \\ / : * ? \" < > |) failed at once with exit code 1 and nothing created; a valid name passed through, and fresh install and re-run, the comma-joined -Roots case, the non-pwsh -PwshPath refusal, and positional-argument refusal all behaved as in v0.3.1. The v0.3.0 and v0.3.1 installer rehearsals stand as recorded in those sections. The gaps those rehearsals never exercised are unchanged by this version: a fresh install with the default watched folders, machines without PowerShell 7, and the logon trigger and 15-minute repetition (rehearsal tasks were started by hand).
- PowerShell 7 is required for the File Save Log module, and File Save Log is Windows-only in this version. Mac support for File Save Log is planned for a later version.
- The upgrade prompt (prompts/upgrade.md) remains UNRUN on a real board. The first pilot upgrade to this version is its first real run: it diagnoses before it changes anything, backs up first, and waits for the user's yes at every data-changing step.
- Task source keys with server-side dedupe for the brief's Add to To-do's (a data-model change) are not in this version. They are designed and held for v0.3.3, gated on the upgrade prompt covering the migration and on a clean-room rehearsal proving an upgrade preserves all existing data.

Detailed entries:

- Brief reader button row (spec/EMAIL-BRIEF.md section 6, self-check item 18): each bullet's actions row, holding the Open pill and then the Add to To-do's button (or its Added state), is now specified aligned to the far right of the bullet's block, with slim controls (reduced vertical padding, line-height 1.2). The row still sits directly under the bullet's text, never inline and never split.
- File Save Log installer validates -TaskName first (filesave-log/Install-FileSaveLog.ps1, spec/FILE-SAVE-LOG.md section 2d): the task name is checked at the very start of the script, before any file is copied, any config is written, or any scan runs. A name that is empty after trimming, or that contains a character Windows Task Scheduler forbids in a task name ( \ / : * ? " < > | ), fails at once with a clear message and exit code 1, with no side effects. In v0.3.1 an invalid name was caught only at registration, after the install work was already done. The validation is syntax only: it does not detect a collision with an existing task of the same name, and registering under an existing name overwrites that task, by design.
- Panel entry control renamed from Edit to Details (spec/SPEC.md sections 3.6 and 9, spec/FILE-SAVE-LOG.md section 4): the per-entry control on a panel item row that opens the item editor is now labeled "Details", because the editor holds more than the row shows. Other Edit labels are unchanged: "Edit categories", the "Edit window" wording for editor dialogs, and the entry detail line that reads "'Edit' to change times" all stay as they were.
- Dialog closing unified (spec/SPEC.md sections 2.8 and 3.6, self-check item 12): every modal dialog carries a bare corner X in its top right corner. On editor dialogs (the panel item editor in all its forms, the Categories taxonomy editor, the routine entry editor) the X does exactly what Cancel does, and the editor's footer Cancel is never disabled. Closing a dirty editor by any path (the X, Cancel, Escape, or a backdrop click) shows one warning headed "Changes will be lost" with "Keep editing" and "Discard changes"; a clean editor closes at once with no warning. On confirmation dialogs the X counts as the cancel choice. The File Save Log FILTER modal's corner X does what its Close button does, and FILTER gains no Escape or backdrop dismissal. A gold footer button still marks a dialog that carries a decision.
- Email Brief screening silence (spec/EMAIL-BRIEF.md sections 3.2 and 7): when at least one generic LinkedIn InMail recruiter message is screened in a window, the brief carries exactly one tally line at the end of FYI, "Screened: N generic LinkedIn InMail recruiter message(s)". When nothing is screened, the brief says nothing about screening anywhere, including its coverage line, which states the inboxes swept and the window covered and nothing about screening.
- Email Brief stack order within a day (spec/EMAIL-BRIEF.md section 7, prompts/03-email-brief-setup.md, self-check item 18): each day's briefs are now collected newest first, in reverse slot-time order (the day's latest brief first, its earliest last), matching the days order, so the whole combined stack reads newest on top throughout.
- Item-create field quirk documented (spec/SPEC.md section 6): the board's addpanelitem create action silently ignores the detail and status arguments (the call succeeds; the item lands with its detail empty and the default status), while url is honored on create. The spec now records the verified three-step write pattern for programmatic item creation (create, then set detail and status with updatepanelitem, then read the item back), and the bridge consequence: a bridge add-panel-item that carries a detail must be followed by the update step in the same pass.

Reason: scripts from before the kit carried its own scanner, including ones a setup generated on the spot, have no marker, and an unmarked script's date proves nothing about its freshness. ## 0.2.1 (pilot) - 2026-11-05

Categories and subcategories get a real home the user controls, instead of a list built into the board.

- Taxonomy table: the Category and SubCategory preset lists now live in board-owned storage as one editable taxonomy table (categories in order, each with its ordered subcategories), specified in spec/SPEC.md section 2.8. getdashboard returns the table, so backups include it, and two new board actions, gettaxonomy and updatetaxonomy, read and save it. The board now publishes 25 actions.
- The table ships empty. The kit ships no categories or subcategories at all, and the seed carries the table as an empty list. The setup interview now also collects the user's subcategories for each category, and the Email Brief setup step writes the user's own categories and subcategories into the table at install, then reads the table back for confirmation. That table is the one source for both the board's dropdowns and the Email Brief's category suggestions, replacing any separate brief-only list.
- An editor in the expanded To-do's lets the user add, rename, and remove categories and subcategories. A rename first shows the old value, the new value, and how many tasks carry the old value, and rewrites those tasks only if the user confirms updating them; subcategory renames are scoped to their category. A removal never deletes, completes, or hides a task: it offers to reassign the affected tasks to another value, or leave their values standing as free text. Removing a category removes only its subcategory list from the table.
- Free text is unchanged: Category and SubCategory still accept any typed value, and a value that is not in the table displays and edits normally in the drawer, the filters, Batch grouping, and search. It simply gets no presets.
- The self-check and repair prompt now checks the taxonomy table and its editor, including the rename and remove confirmation rules and free-text entry. The upgrade prompt states explicitly that an existing user's taxonomy table is user data: an upgrade preserves it verbatim, never reseeds it, and never overwrites it, and reads it back after the upgrade to prove it.

## 0.1.4 (pilot)

The install is now guided. You no longer read instructions or paste a series of prompts yourself.

- New front door: 00-START-HERE.md, at the front of the kit (and sendable on its own, ahead of the kit). You hand that one file to your Muse and type one sentence, "Follow the file I gave you and start my install." Your Muse then conducts the entire install in conversation: it introduces what will happen, gets the kit files into place with you (if your Muse can work with files, you just upload the kit zip and it unpacks and verifies the set; if not, it walks you through unzipping and asks for each file when it needs it), then runs the six install steps in order, one question or action at a time, explaining anything you have to do on your own computer before you do it and interpreting what comes back.
- Checkpoints and pauses are built in: each step ends with a verified summary you confirm, you can pause at any point and resume in a fresh conversation (your Muse keeps a small install-state file and re-reads your board, which is the ground truth), and if something goes wrong your Muse stops, troubleshoots once, and either fixes it or parks that one module and carries on with the rest. Nothing is silently skipped, and nothing is marked done that was not verified.
- INSTALL.md and README.md now present the guided route first. The six-step manual route is unchanged and remains as the reference and the fallback; the step prompts, specs, and board behaviour did not change in this version.

## 0.1.3 (pilot)

File Save Log setup is now checked before it is installed, instead of being discovered by failure.

- New pre-install diagnostic: a script in the kit's preinstall folder that you run once on your main computer before the File Save Log setup, which checks the module's machine requirements live: Windows version, that you are in a logged-on session, PowerShell 7 and its real path on your machine, the windowless scanner launch (tested for real, not read from settings), Task Scheduler including a create-and-delete test task, access to the folders you want watched and to your log destination, and whether your cloud folders are visible from your session. It writes a short dated report that you paste to your Muse; setup uses its results and paths, and anything it marks FAIL is fixed and rechecked, or the module is parked, before anything is installed. It installs nothing itself, runs on the PowerShell built into Windows (so it works on machines that do not have PowerShell 7 yet), and its few test files clean up after themselves.
- The File Save Log install steps are rewritten around that report: a preflight before setup, a fuller setup interview (folders your own tools work in are excluded for you, the shipped exclusions are read out loud in case one would hide real work of yours, a plain privacy note that the log records file names and paths, and honest expectations about scans pausing while you are logged out, scan time, and the occasional save showing up one cycle late), explicit setup rules with no substitutes, and a verification step that now asks you directly whether any window appeared and measures how long your scanner actually takes.
- The spec now states the scanner's core safety rule in its own words: it records metadata only and must never open, read, or copy a watched file, because reading a cloud file that has not downloaded yet would force it to download.
- The Privacy file now says plainly that the log's content is file names and full paths, which can themselves be sensitive, so choosing folders and the log location is a privacy choice.
- A correction to the 0.1.2 notes below: the windowless wrapper on the reference install, described there as prepared but not yet applied, was in fact applied and verified later that same day, with the scanner running a full cycle and no window appearing. The pre-install diagnostic has also run live on the reference machine since then, with every check passing. Neither result proves anything about your machine, which is the point of running the diagnostic there; they do mean the designs in this release are not untested.

## 0.1.2 (pilot)

One setup fix for the File Save Log on Windows, learned from real use: a scanner window flashing (or worse, lingering) every 15 minutes is disruptive enough to make people drop the module.

- The File Save Log spec now requires a completely windowless scanner launch on Windows: run the scanner through a small wscript.exe VBScript wrapper that starts it hidden from the moment the process is created and passes its exit code back to Task Scheduler. Launching PowerShell directly with a hidden-window flag is explicitly not sufficient (Windows creates the window before the flag applies, and the flag can be ignored after updates). Fallback: conhost.exe --headless where VBScript is blocked.
- The spec also forbids the tempting wrong fix, running the scheduled task outside the user's logged-on session, because mapped cloud drives may not exist there and scan output can silently stop arriving.
- Windowless counts as verified only when the user confirms a cycle ran with no window seen, never from task settings alone.
- The reference install this was learned from has the wrapper prepared but not yet applied as of this kit version; the kit carries the design, and pilot installs will be its first live test.
