# File Save Log Specification (scoped v1)

Version: current kit version (see the VERSION file at the kit root)
Module: File Save Log. It fills the File Saves History panel with the files the user actually saved, so they can find recent work from the board.

Read section 6 first. This is the kit's most fragile module, by design honestly labelled, and it is the last thing installed.

Platform: Windows-only in this version. The scanner, its one installer, the pre-install diagnostic, and the windowless launch are all Windows components (PowerShell, Task Scheduler, wscript). On macOS this module is skipped: a Mac install records File Save Log as skipped by platform, not as a failure and not as a parked module, and the rest of the kit works on macOS unchanged. Mac support for File Save Log is planned for a later version.

## 1. Scope

- One main computer (the user's). Multi-computer merging is not in this version.
- Folders: the ones the user chose in the module interview (typical: Documents, Downloads, Desktop, and the user's Muse workspace). Nothing outside the chosen folders is watched.
- Panel output: all panel-eligible saves in the retention window are published to the panel (section 4c); the panel displays up to the panel-size setting (default 40) after filtering, newest first.

## 2. Components

a) Scanner, on the user's computer: a small script, set up with the user's explicit approval, that records file saves in the watched folders (file name, full path, folder, save time, whether the file is new or updated) into a local log file. It must be set up so it restarts with the computer, and the setup must verify that it is actually running after setup, not merely installed. On Windows it must also run completely windowless (section 2c); a scanner window appearing every 15 minutes is a setup failure, not a cosmetic issue. It records metadata only and must never open, read, hash, or copy a watched file: reading a cloud placeholder file (a OneDrive or Drive file that is not downloaded yet) would force that file to download, so content access is forbidden by design, not merely unnecessary.

b) Aggregator, a scheduled job in the user's Muse every 15 minutes, which:
1. Reads new scanner log entries since the last run (keep a watermark; never re-read the whole history).
2. Reads the board's Dismiss and Hide-always lists (section 4) as part of the dashboard state it syncs against; those lists are board state, set from the panel, and the aggregator never infers them from missing rows (detection by absence is retired, section 4).
3. Applies exclusions (section 3) and the panel-only rules, then publishes every panel-eligible row in the retention window (the panel-size setting, default 40, caps what the panel displays, not what it receives). Dismiss and Hide always are applied by the board's rendering, not by removing rows from the payload.
4. Syncs the File Saves History panel to the result: add new entries, update changed ones, remove entries that rolled off the payload, change nothing else on the board.
5. Appends everything (including excluded entries) to the master log, and refreshes the full-log file in the location the user chose (their Drive, or a local file).
6. Exports the board's dismiss and hide-always lists to a local state file that the explain tool reads (section 4).

c) Panel entry format: title is the file name. Detail line: location label (the watched folder's short name), the name of the folder the file sits in (omitted when the file sits directly in a watched folder, when that folder's name is the location label itself, or when the parent folder is a watched root whose on-disk name is the location label plus a qualifier, such as an organization name), status (New or Updated), last saved time, and the day's save count. Notes carry three lines: Date (YYYY-MM-DD), Folder (full path of the containing folder), Full path. The hide key is "<date>|<full path>". The pinned full-log entry (section 4, last paragraph) is separate.

## 2b. Pre-install diagnostic

Setup for this module begins before anything is installed, with the diagnostic the kit ships at preinstall/Check-FileSaveLogRequirements.ps1 (see INSTALL.md step 5 for how the user runs it). Design points that matter:

- It runs on the Windows PowerShell that ships with Windows (5.1) on purpose, because PowerShell 7 is one of the requirements it checks; a diagnostic that needed PowerShell 7 could not run on the machines that most need it.
- It checks the machine-side minimum requirements live, not from settings: Windows version and build (including whether the Windows 11 headless fallback exists), an interactive logged-on session, PowerShell 7 presence, version, and its real resolved path on that machine, script host present and not policy disabled plus the live windowless test in section 2c's pattern, the Task Scheduler service plus a real create, read back, and delete task test under the user's own account, read and write access on the watched folders and the log destination, and which cloud folders and sync apps are visible from that session.
- It is check-only and self-cleaning: its only writes are small test files it deletes in the same run, the temporary test task, and its report file. It installs nothing and changes no setting.
- Its output is a dated plain text report the user pastes to their Muse. Setup consumes the report: its verdict gates installation (any FAIL is fixed and the diagnostic rerun, or the module is parked, before anything is installed), and its measured paths and versions are the ones setup uses.
- A passing report is evidence about that machine, on that day, in that session. Like every verification in this kit, it does not transfer to another machine or another user.

## 2c. Windowless launch on Windows (scanner)

The scanner runs every 15 minutes on a machine the user is actively working at. Any window it shows, even a brief one, is disruptive; a window that lingers for the length of a scan is unacceptable. Set the launch up windowless from the start:

- Do NOT create the scheduled task action as a direct PowerShell launch. A flag such as -WindowStyle Hidden is not sufficient: Windows creates the console window first and PowerShell applies the flag afterward, so there is always at least a flash, and the flag can be ignored entirely (observed after a PowerShell update, when the scan window stayed fully open for the whole run).
- Instead, the task action runs a tiny VBScript wrapper through wscript.exe. wscript.exe has no console window of its own, and the wrapper starts the scanner process with window style 0 (hidden from the moment the process is created), waits for it to finish, and returns its exit code, so Task Scheduler still tracks start, end, result, and the run time limit exactly as it would for a direct launch. The wrapper changes only how the scanner is launched: not the scanner script, not the triggers, not the task settings. Reverting is restoring the direct action.
- Fallback, if VBScript is blocked on the machine: launch through conhost.exe --headless (Windows 11).
- The task's own "Hidden" checkbox in Task Scheduler is not a substitute; it hides the task in the Task Scheduler list, not its window.
- Never fix window visibility by switching the task to "run whether the user is logged on or not". That runs outside the user's desktop session, where mapped cloud drives (for example a Drive letter for cloud storage, or a synced OneDrive) may not be mounted, so scanner output can silently stop landing where the aggregator reads it. An invisible failure is worse than a visible window.
- Verification: windowless counts as working only when the user confirms a scheduled cycle ran with no window seen at all. Do not claim it from the task settings alone (same honesty rule as section 5: verify from the cycle, not from configuration).

## 2d. The installer (one, idempotent, never downgrades a marked script)

The module's computer-side piece is the scanner, and it is installed by exactly ONE script, `filesave-log/Install-FileSaveLog.ps1` (PowerShell 7). There is no separate add-on installer, and setup never needs one: the one installer installs or refreshes the scanner, generates the windowless-launch wrapper with the machine's resolved pwsh.exe path and install folder baked in (section 2c; conhost.exe --headless for the task if wscript.exe is unavailable), installs the shipped excludes defaults, creates the user's excludes file from the template only when absent (section 3b), creates config.json only on a fresh install (an existing config is preserved exactly), and registers the one scheduled task (named by the installer's -TaskName parameter, default FileSaveLog-Scan, at logon and every 15 minutes; interactive logon, Limited, never "run whether logged on or not"). An earlier kit design also installed a scan-request watcher component (a script and a second task that polled the outbox for trigger files). It was removed from the kit: nothing in the manual Update chain (section 4d) consumes a trigger file, so the component did nothing. The installer neither installs nor manages it, and does not remove one a machine may already have.

- **Never-downgrade rule (marked scripts).** The packaged scanner carries a `$ScriptVersion` marker near the top. When the installed copy also carries a marker, the higher marker wins: packaged newer, upgrade (the previous copy is first backed up beside it as `<name>.bak-<timestamp>`); equal, already current, nothing copied; installed newer, the replacement is skipped, the installed file is left untouched, and the summary reports the component as "kept (installed is newer)" with a warning naming the file. This rule exists because a packaged script can legitimately be older than an installed one that was updated after packaging; an unconditional copy would silently downgrade it. The never-downgrade rule applies only between two marked scripts.
- **Legacy rule (unmarked installed scripts).** An installed scanner with NO `$ScriptVersion` marker is legacy, never "newer", whatever its file date says: scripts from before the kit carried its own scanner (including one a setup generated on the spot) have no marker, and their dates prove nothing. The installer backs the legacy copy up with the same timestamped name, replaces it with the packaged script, and prints a clear warning that an unmarked (legacy) script was replaced. File dates are never consulted for any script decision. One shortcut stands in front of both rules: identical content (SHA256) is always already current, so an identical file is never replaced regardless of markers. And if a packaged copy somehow carries no marker while the installed one does, the marked installed copy stays: a package that cannot prove its freshness never displaces a marked install.
- **Idempotent.** Re-running the installer on an up-to-date install changes nothing: the scanner and the wrapper compare as already current, the defaults file compares identical, the user excludes file and config.json are preserved, the task is re-registered with an identical definition, no baseline scan runs (a fresh install runs one), and the script exits 0 with a per-component summary (installed / upgraded / already current / kept (installed is newer) / created / preserved / registered / run / skipped / fallback used). Three of those words describe actions rather than files: run (an action was executed, for example the baseline scan ran on a fresh install), skipped (a step that did not need to run, for example the baseline scan on a re-run), and fallback used (a fallback path was taken, for example the local outbox fallback or the conhost.exe --headless launch fallback). Any component that fails is reported FAILED in the summary and the exit code is 1.
- **Parameters, not edits.** The installer takes the machine's real values as parameters (install folder, watched roots as "Path|Area" entries, outbox, pwsh.exe path, and the scheduled task name, -TaskName, whose default is FileSaveLog-Scan), which setup supplies from the pre-install diagnostic report and the module interview. Nobody edits the installer to install it.
- The installer does not install the optional local-files extra (click-to-open handler); that remains a separate, optional step (section 6).
- **Rehearsal safety.** A rehearsal on a machine that already has a live install MUST pass a distinct -TaskName and a scratch -InstallDir. A task name is the one name the installer uses that is not scoped to the install folder: task names live in the machine's shared task store, so a rehearsal run under the default name would register over the live task and point it at the scratch folder. With a distinct name and a scratch folder, the rehearsal never reads, registers, or overwrites the live task, and never touches the live install folder.
- **Status: REHEARSED.** The installer was rehearsed by Claude Code on Windows with PowerShell 7 on 2026-11-08, in a scratch folder with a distinct task name and a scratch install folder, so the live install on the same machine was untouched. All five scenarios in the checklist below passed, and the failure path passed too: an invalid input produced FAILED and exit code 1, and registered nothing. The rehearsal did not cover everything; a pilot's first real install is the first test of a visual confirmation that nothing flashes on screen during the hidden launch, the conhost.exe --headless fallback for when wscript.exe is unavailable, a fresh install using the default watched folders or the automatic Google Drive outbox detection, and a machine without PowerShell 7 or with a different user profile layout (the full list is in the CHANGELOG's known limitations for this version). Rehearsal checklist (run 2026-11-08, all passed), always into a scratch -InstallDir and, on any machine that already has a live install, under a distinct -TaskName (the rehearsal safety rule above), so the live task is never read, registered, or overwritten: (1) a fresh install; (2) a re-run on the up-to-date install from scenario 1 (nothing copied, exit 0); (3) an install whose scanner marker is newer than the package (kept untouched, warning shown); (4) an install whose scanner marker is older than the package (upgraded, previous copy backed up); (5) an installed scanner with no marker and a file date NEWER than the packaged copy (it must be backed up and replaced, with the legacy warning; the date must not save it).

## 3. Exclusions and panel-only rules (the layers)

What a save hits, in order (the full layer table is Section 3c):

- **Complete exclusions** (never in the panel, the master log, or the CSV): the config-driven rules of Section 3b. The shipped defaults cover machine output only: temporary and partial downloads (.tmp, .temp, .crdownload, .partial, .part), application sidecars and locks (.log, .swp, .swo, .pyc, .etl, .asd, .wbk, .lock, -wal, -shm, -journal), housekeeping names (desktop.ini, Thumbs.db, .DS_Store, ~$*, ~WRL*.tmp, LibreOffice locks), generated build files (next-env.d.ts, *.tsbuildinfo), and tool and system folders (.git, node_modules, __pycache__, virtualenvs, .cache, editor folders, recycle and trash folders, Drive transfer temp folders). Optional groups ship disabled (.bak files, build folders, Snagit .snagx captures, screenshot folders, and an example generated-output pair); a user enables them in their own file.
- **Panel-only rules** (kept in the master log and CSV, never on the panel): the patterns live in the `panelOnly` block of the same two config files (Section 3b), never in code. The shipped defaults carry only Temp and tmp folder segments. Everything user-specific belongs in the user's own file: their staging folders, handover-file name patterns, shortcut files (.lnk) if they choose, and path prefixes for whole trees they work in but do not want on the panel (for example their development folder).
- **Behaviors, in code only**: Dismiss, Hide this file always, and the link test (Section 4) are behaviors, not patterns; they live in the board and aggregator code and have no config entries.
- The user's own automation working folders are a per-user config entry at setup (for example the output, logs, and attachments folders of a scheduled search tool they run, as segment pairs, plus its state file names). Per-user, never a shipped default.
- Matching discipline: file-name, suffix, folder-segment, adjacent segment-pair, and path-prefix matches, all case-insensitive, never a substring search over the whole path.

Deliberately NOT excluded by the shipped defaults. These were considered and rejected; do not add them as defaults, and flag it if a setup conversation drifts toward them, because they hide real work:

- Screenshot and screen-capture files as a class (a user may still enable the optional screenshot or .snagx groups for their own setup)
- Same-day duplicates of the same file in two locations (no dedupe by name or across locations; the same-path, same-day panel rule in section 4c is a display rule, not an exclusion)
- Project instruction files (for example CLAUDE.md)
- Folders named Templates, and files with "Temporary" in their name (substring lookalikes are not matches)
- Photos, anything in Downloads, and Save-As versions of a document

The user may add exclusions of their own beyond the defaults by asking; whoever applies the change restates its effect first (complete versus panel-only) before applying it.

## 3b. Exclusions are config-driven (one design, two files)

- The scanner and the aggregator read the SAME two JSON files, so they can never drift apart. `FileSaveLog-Excludes.json` ships with the kit and is replaced on every kit update; it holds the shipped defaults and a block of optional rule groups that ship disabled. `FileSaveLog-Excludes.user.json` holds the user's own rules and is never overwritten; the installer creates it from `FileSaveLog-Excludes.user.template.json` and fills its `selfPaths` with the user's own scanner, batch, state, and ingest folders (the feedback-loop guard).
- Schema: `extensions` (a name ending in the entry; dot entries match the extension, suffix entries like `-wal` match the name ending), `fileNames` (wildcards allowed), `folderSegments` (one path segment anywhere), `segmentPairs` ([parent, child], the child folder directly under the parent, so unrelated folders named cache or Output are untouched), `selfPaths`, and `enableOptional` in the user file to switch on shipped optional groups (for example Snagit .snagx captures, screenshot folders, build folders, .bak files).
- The kit ships the shared loader (`filesave-log/excludes.py`, used by the aggregator and the scanners) and the explain command (`filesave-log/explain.py`, see Section 4) with the module.
- A `panelOnly` block in the same two files carries the record-only rules, with the same rule types plus `pathPrefixes` (absolute path prefixes). The shipped defaults carry only generic entries (Temp and tmp folder segments); a user's private entries (their staging folders, their dev-tree prefixes) belong only in their user file. The scanner ignores the panelOnly block; only the aggregator and the panel apply it.
- All matching is case-insensitive. The Section 3 lists above describe rule CONTENT; this section is the mechanism, and the shipped defaults file is where the current content lives.
- Fail-safe: if a config file is missing or invalid, the scanner and the aggregator fall back to a small built-in minimal set (transient downloads and lock artifacts only), write a visible warning to the scanner's log, and keep running. A bad config never crashes the scan and never excludes everything.
- Personal rules (a user's own tool-output folders, private segment pairs) belong only in the user file, never in the shipped defaults.
- Two numbers are settings, not constants: `panelSize` (saves shown in the panel, default 40, valid 10 to 200) and `retentionMonths` (months kept in the master log, default 12, valid 1 to 60). They ship in the defaults file's `settings` object; the user file may override either key. An invalid value (out of range, not a whole number, wrong type) falls back with a logged warning: an invalid user value to the defaults value, an invalid defaults value to the built-in 40 and 12. With no override anywhere, behavior is exactly the shipped defaults.
- Lowering retentionMonths takes effect on the aggregator's next run: entries older than the new window are archived and removed from the working log at that point. Raising it again later does not pull archived entries back.

## 3c. The layers at a glance

| Layer | Where defined | Panel | Master log and CSV | Who can change it |
|---|---|---|---|---|---|
| Complete exclusions | Config files (defaults + user), applied by the aggregator and the scanners | Never shown | Never kept | Kit update (defaults) or the user (their user file) |
| Panel-only rules (panelOnly) | Config files' `panelOnly` block, applied by the aggregator | Never shown | Kept | Kit update (generic defaults) or the user (their entries) |
| Link test | Aggregator code | Shown only if the path makes a working link (Windows drive, UNC, macOS user paths) | Kept | Kit code |
| Dismiss (one save) | Board state, set from the panel | That save hidden; a newer save of the file returns | Kept | The user, in the panel (restorable) |
| Hide this file always | Board state, set from the panel | File never shown until restored | Kept | The user, in the panel (restorable) |
| Extension filter and Show x | Board state, set from the panel | Narrows what is displayed; rows are still on the board | Kept | The user, in the panel (Reset filters clears) |
| Retention window | Config setting `retentionMonths` | Rows older than the window are gone | Archived by year, then removed | The user (config), with the archiving safeguard |

## 4. Panel delete: Dismiss and Hide always

- Deleting a panel row offers two actions. **Dismiss** (the default) hides only that save event: the row's day entry is suppressed, and a newer save of the same file shows again. **Hide this file always** mutes the path: no save of that file ever shows until it is restored.
- Both lists live in the board's own durable state. A **Hidden items** view lists dismissals and always-hidden files together, each with a **Restore** action; restoring a dismissal brings that save back, restoring an always-hide lets the file's rows show again.
- Pre-split permanent hides (from the earlier delete model, keyed "<date>|<full path>") migrate to Hide-always entries for their paths, so nothing already hidden reappears when the split model ships.
- Detection by absence is retired: a row missing from the displayed list is never, by itself, treated as a deletion. The aggregator no longer guesses hides from panel snapshots.
- Post-edit caution: after any automated edit to a store the user also edits (these hide lists, the panel, the master log), a missing record is not automatically data loss. Confirm it was not an intentional deletion by the user before restoring anything. This is the same check OPERATING-RULES.md rule 14 states generally.
- The pinned entry, titled "Full Log of File Saves", linking to the full-log file, always sits at the top of the panel above the saves and never counts toward them. It carries no Date or Full path notes, and the aggregator re-adds it if it is removed.
- Rows in this panel are owned by the sync, so they render without the leading dot other panels show and without an Edit control (the pinned row included): their only row controls are Dismiss, Hide always, and Copy path. A manual edit would be overwritten by the next sync cycle and could disturb the row's event key, so the affordance is removed rather than left as a trap. Other panels keep their dots and Edit unchanged.
- A "Why isn't this shown?" section in the filter modal (section 4c) answers from the board's own state (Dismiss, Hide always, filtered out, beyond the shown count), and its FILE PATH TO CHECK field runs one pasted path through every layer and names the first layer that hides it. For the exact config rule behind a complete exclusion or a panel-only rule, the user can ask Muse "why isn't <path> shown?" and Muse runs the kit's checker against the config, or the user can run it themselves if they have Python 3: `python3 explain.py "<full path>"` in the filesave-log folder (it uses the same loader as the aggregator and reads the two config files beside it). The panel dialog gives both options.

## 4c. Panel filters

- The panel receives **all** panel-eligible rows in the retention window (not just the top panelSize), so filtering is honest. Rows arrive newest first.
- **Same-day dedupe (panel display rule, not an exclusion):** within one calendar day (the user's timezone), the panel shows only the most recent save of a given file. A duplicate is the identical full path, filename included, compared case-insensitively. The aggregator collapses same-day rows for one file into the latest save's row, with the day's save count summed and the day's first-save time kept, before the payload is published, so the Show x cap (panelSize) applies to deduped rows. A save of the same file on a different day keeps its own row (a file can appear once per day). The master log and the CSV keep every save regardless; nothing is excluded or deleted. Because the payload holds exactly one row per file per day, dismissing that row leaves no earlier same-day save to resurface; the file returns with a later save.
- **File Extensions** filter (the modal's extension section): one checkbox per extension present among the panel-eligible rows (after exclusions, panel-only rules, the link test, dismissals, and always-hides), with a count per extension, grouped case-insensitively, plus a "(no extension)" entry, and two buttons beside the heading: Show all (checks every extension; the Show count is untouched) and Clear all (unchecks every extension). The board stores the UNCHECKED set, so an extension that appears later is shown by default.
- **Show x files**: how many rows are displayed after filtering, from 1 up to the panelSize setting (default 40). The status line reads "Showing N of M matching" with the eligible-of-received counts beside it; an empty match shows a clear empty message.
- Both selections persist in the board's durable state across reloads and sessions. **Reset Filters** (in the modal's header) clears the saved selection entirely (all extensions checked, show count back to panelSize), and also resets the section views: it closes whichever modal section is open, clears the section highlight, and clears the FILE PATH TO CHECK field together with any verdict or error, so the section reopens fresh. It does not restore or alter hidden items, does not touch the Rules dialog, and cannot resize or move the modal. The default Show count itself is a board setting with two doors to the same stored value: the modal's Show count and the Settings dialog (SPEC.md section 9).
- A small footer on the panel reads "N hidden (no link)": rows kept in the log that failed the link test in the current window.
- Filename rendering: a file save entry's filename is not bold. It renders the way filenames render in Windows File Explorer: regular weight, Segoe UI (with the board's sans fallbacks), at the panel's normal text size, in the standard text color. The pinned full-log row at the top is a link label, not a filename, and keeps the panel's normal title rendering; panel item titles in other panels are unaffected.
- Presentation: the filter controls (the File Extensions grid, Show all / Clear all, Show count, status lines, and the Hidden items, Why isn't this shown?, and Rules controls) live in a floating filter modal over the panel, not inline at the top of the panel. The modal is titled "FILTER"; its header carries, in order, Reset Filters, Minimize, and Close. The modal's fill is a light subdued greige (a muted warm paper tone that sits calmly against the dark board, not pure white), with its text and controls recolored dark for contrast, scoped to the modal only (headings in a darkened amber, buttons a slightly deeper greige with dark text and visible borders, status lines dark gray); the file entries start at the top of the panel body and scroll under the modal, which stays visible while scrolling. The modal can be dragged anywhere on the board screen by a grip in its header that matches the workstream panel header grip (same glyph, styling, and arrow cursor), and keeps its dragged position while open (it may reset on reload); only the grip needs to stay reachable on screen. Buttons, checkboxes, and links inside the modal are never drag starters. The modal opens on the Filter link in the panel's stamp row, and it also opens by itself when the panel goes from collapsed to expanded: a transition-only effect, so a panel that loads expanded never auto-opens, and if the modal is already open at the transition it is left exactly as it is. On auto-open it comes up in its default view: the measured default size (the size on first open with sections closed) committed as the saved size, both sections closed, the saved extension and Show count state NOT reset, and a position dragged earlier in the page session restored, clamped to the viewport. On open, if the panel-anchored starting position would fall outside the visible viewport (for example when the panel sits low and its header is below the screen's bottom edge), the modal shifts so it opens fully in view, above the panel's on-screen position; once open, the user's dragged position rules. Minimize reverts the modal to its measured default size (the collapsed bar of an earlier design is gone; there is no Expand button): position is preserved, re-clamped to the viewport, the reverted size becomes the stored size, and a section that is open stays open at the default size. The modal can also be resized by hand: a diagonal-stroke grip at its bottom-right corner (pointer capture; arrow keys resize it when focused), with the measured default size as the minimum, enforced in the drag and as inline minimum width and height, and the viewport as the maximum. A chosen size persists across Close and reopen while the page stays open and resets on a full page reload. Closing hides it while the panel stays expanded; it returns only when the panel is collapsed and expanded again, or when the user clicks Filter.
- Sections inside the modal: "Hidden items" and "Why isn't this shown?" are driven by a single open-section state, so they can never stack; the open section's button carries a solid gold active treatment, and the Rules button carries the same treatment while its dialog is open. Opening a section grows the modal's height by exactly that section's overflow (height only, grow-only: closing a section never shrinks it), capped at the viewport with an 8px margin, shifting the modal up if needed, with internal scrolling as the fallback; a grown size persists like a manual resize. The "Why isn't this shown?" section shows, in order: a status line, the FILE PATH TO CHECK field (an auto-growing text area in the board's link-target styling, with the standard green entry fill; literal line breaks are stripped on submit) with its Check button and the result directly below it, then the two explainer paragraphs at 12px. The first sentence of the first paragraph ("Use this when a file you saved does not appear in this panel.") carries an amber marker highlight in the modal's palette, background only. The second paragraph ("Changing rules:") renders as a gold-bordered callout.
- Row views, Expanded and Compact: entries render in one of two views, switched by a row-density toggle at the extreme right of the panel's stamp row (tooltip and aria-label "Switch to compact view" in Expanded, "Switch to expanded view" in Compact). Expanded is the full rendering (filename full width, detail line under it, and the Copy path, Dismiss, and Hide controls always on one left-aligned line at the bottom of the entry; the pinned row follows the same structure with Copy path alone). Compact renders each entry as a single-line name-only row (no detail line, no action line, no separators); the pinned row appears first, still name-only, and carries the same header band fill it has in Expanded view. Compact is the panel's initial view on page load, and every collapse-to-expand transition resets the view to Compact; while the panel stays open, the toggle holds whatever the user picks. Every entry also carries a small chevron button immediately to the left of its filename, in a fixed leading slot so filenames stay aligned in both views: chevron down while the entry is in its expanded rendering, chevron right while it is compact, with "Show less" and "Show more" labels and tooltips and aria-expanded state. Clicking it toggles that entry only; entries follow the panel view by default, a per-entry toggle overrides the panel view for that entry, and flipping the panel-wide toggle, or the panel reopening into Compact, clears all per-entry overrides. View state and overrides are page-session state only; nothing is stored on the server.
- Long filenames: a filename may wrap onto up to 2 lines, and long unbroken strings break across lines so both lines are used. If the full name still does not fit in 2 lines at the row's width, the displayed text is shortened: the beginning of the name, then "...", then the last 12 characters immediately to the left of the file extension, then the extension, with the head sized to fit the 2 lines (measured at the rendered width and font). A name that fits in 2 lines is shown in full. For a name with no extension, the preserved tail is the last 12 characters of the name. The full filename remains the link target and the row's data, and is shown as the row's tooltip.

## 4b. Rolling retention archive

- The master log keeps a rolling retention window (the retentionMonths setting, default 12 months). Entries older than the window are archived before they are removed: grouped by year, one JSON file and one CSV file per year, written into an archive folder beside the master log (or in the cloud location the user chose for the full log).
- Archiving is part of the aggregator cycle, and it is fail-safe: if writing an archive file fails, the whole cycle aborts before anything is published to the panel, so an archiving problem can never silently drop history.
- Archived entries are gone from the working log and the panel, and retrievable from the archive files at any time by asking.

## 4d. Manual update (chat-triggered)

- The flow is manual: there is no watcher job and no automatic update. The user clicks the panel's Update button, pastes the phrase it copies into their chat with the assistant, and the assistant runs the whole chain inline in that conversation (ingest the scanner batches, aggregate, publish the full-log file, sync the panel, stamp completion). It takes about 5 minutes end to end. The computer-side scanner keeps staging batches on its normal 15-minute schedule, so a run picks up saves through the last staged batch.
- The Update button sits in the panel's stamp row, at the left of the standing stamp line. It is a real button in the board's small-button styling, and its label is always "Update": the text never changes in any state. While a request is active (outstanding and not yet resolved) the button takes the muted gray disabled treatment; when the update completes or fails it returns to its regular treatment and is clickable again. Clicking it copies the exact phrase "Update File Saves History" to the clipboard and calls a board action that stamps the current time into board storage as the latest update request (exposed by getdashboard as file_save_refresh_requested_at); the click also clears any previous run-started stamp. The standing line beside the button reads "Last update · <time>", with the weekday and date included for older stamps; a completion counts only when its stamp is at or after the request stamp. If the clipboard write is blocked, no modal appears: the panel shows a guidance note in its note bar instead, and never claims a copy happened.
- Submission is stamped, not inferred. The board also stores a run-started stamp (getdashboard: file_save_refresh_started_at), set through a start action the assistant's run calls as its FIRST step when it picks up the pasted phrase in chat, before any ingest or sync work. A started stamp counts only when it is at or after the outstanding request's stamp, so a stale start can never cover a new request. The submission window is 60 seconds, a single shared constant wherever the rule is computed (the Pending countdown, the in-flight test, and the failure test all read it), so the countdown reaching zero and the failure flip are the same instant by construction. Only a request with no counting started stamp can fail as unsubmitted, once it is older than the window with no covering completion; a started stamp that lands after the failure note has appeared still flips the panel to in progress, because the state is derived from the stamps on every render, never latched. Without the started stamp the board could only compare request and completion times, so a run that was submitted on time but still executing read as never submitted.
- The note bar below the stamp row carries the request's status, one note at a time. The failure note has top priority; the blocked-clipboard guidance outranks the Pending line; with no request outstanding, none of these lines shows.
  - Pending (request outstanding, no counting started stamp yet, not failed): a highlighted gold band (accent border, accent-tinted fill, bold text) with two lines, "Pending user to enter in Muse Chat the following text:" and ""Update File Saves History"", and at the right end a live countdown of the remaining submission window, computed from the stored request stamp plus 60 seconds (never from page-load or mount time, so it is correct after reloads), ticking once a second in m:ss and disappearing with the line at the failure flip.
  - In progress (counting started stamp present, no covering completion yet): a light blue band (fill #bfd9f2 family) with dark navy text, two lines, "Update in progress. It can take several minutes." and "Patience please...", and at the extreme right a live elapsed timer counting up once a second from the stored started stamp, in m:ss.
  - Submission failure (no counting started stamp and no covering completion at 60 seconds): two lines, "Update request did not complete · Requested <time>" and "Request was not submitted to Muse Chat", with a Close (x) icon at the right end of the note (tooltip "Close", accessible label "Dismiss this message"). Close voids the request through the cancel action below.
- Cancel and dismiss run through one board action (the cancel action): it clears the outstanding requested and started stamps and never touches the completion stamp, so voiding a request can never fake a completion or move the "Last update" line. It backs the guidance modal's Cancel update button and the Close icon on both failure notes. A completion stamp that lands afterward for a voided request is the no-outstanding-request case: it updates the standing line and does not pop the completion modal.
- A started run is not in flight forever. If a request has a counting started stamp but no covering completion 15 minutes after the started stamp, the panel replaces the in-progress display with a failure note ("Update did not complete · Requested <time>" / "The update started but did not finish within 15 minutes.") carrying the same Close control as the submission failure note; Close voids the request through the cancel action (the requested and started stamps are cleared, the completion stamp is untouched). The completion stamp is what clears a healthy run, and a covering completion that lands after the died-run note appears still wins and replaces it. The 15 minutes is a single shared constant wherever the rule is computed.
- The guidance modal appears on a successful Update click (clipboard copy succeeded). Heading "Update File Saves History", with no icon beside it. A gold callout band reads "You must manually request Muse to do the update". The next line, in the board's full-strength text color for contrast, reads: The request ("Please update File Saves History") is in your clipboard; just paste it in Muse Chat to trigger the update. Then "It will take about 5 minutes to complete." and "A pop-up will announce completion, so feel free to move away to do other work." Across a divider sit the two actions, clearly separated in consequence: "Got it" (gold, primary; closes the popup only, the request proceeds) and "Cancel update" (visually secondary; aborts the request through the cancel action, then closes). Escape and backdrop clicks close without aborting, equivalent to Got it. The last line is visually quiet: "This popup will auto-close in N seconds", where N is a live countdown from 15 to 1 driven by the same mount-anchored deadline that closes the modal, so the number and the close can never drift apart and the panel's background re-renders cannot restart it; the number's color is the default while N is 11 or more, yellow at 10 through 6, and red at 5 through the end, and the grammar is singular at 1 ("in 1 second"). There is no phrase chip or snippet element in the modal; the sentence above names the request. Re-clicking Update while the modal is open restarts the countdown through a remount.
- Completion is signalled, not assumed. The board also stores a completion stamp (getdashboard: file_save_refresh_completed_at), set through a completion action the aggregator calls at the end of EVERY cycle, automatic cycles included; the action stamps on every call and reports whether it covered an outstanding manual request ("covered_request" or "cycle").
- The completion pop-up: heading "Update complete!", then "Files saved since the last update were added to File Saves History", then the day, date, and time on its own line, then OK. It pops once, when a covering completion is first observed while the page is open with that request outstanding; it never pops on page load for an already-covered request, and never for the failure state. The arming is keyed to the request stamp itself and mirrored to the browser's local storage, so it survives a board reload mid-run (the normal case, since the run happens while the user is in chat); the arm is consumed only by a render that can actually judge the outcome (a vanished request stamp, from a cancel or a dismiss, disarms without popping, and a superseded request likewise). The failed-state suppression yields to a counting started stamp: a request that passed through the failure state, then started, then completed covered still pops. Completions discovered more than 15 minutes late disarm silently rather than popping stale news. While a request is in flight the panel re-reads the stamps every 5 seconds, and returning focus or visibility to the board triggers an immediate re-read.
- Generic naming note: the strings in this section name the chat the way the reference build's users know it ("Muse Chat", "Muse"). A build uses the name of the chat the user actually pastes the phrase into, in the same sentences; the mechanism never depends on the name.

## 5. Verification (from the cycle, not by hand)

A change to this module counts as working only when a normal scheduled cycle's own output shows it: saves appearing, exclusions holding (zero excluded names in the panel), hides sticking across two cycles. Never verify by pushing the panel manually; a manual push can race the cycle and create duplicates. Setup's test save (prompts/05) is verified the same way: wait for, or run, one aggregator cycle and read the panel back.

## 6. Honest limits and the parking rule

- This module watches a real computer. Paths, tools, and habits differ per person, and any part (scanner install, restart behaviour, path formats) can fail for local reasons the kit cannot foresee.
- Setup therefore has exactly one troubleshooting pass (TROUBLESHOOTING.md). If the checks still fail, park the module: disable the scanner schedule and the aggregator job, remove nothing from the board (the empty File Saves History panel stays, or the user may delete it), and tell the user plainly it is parked to a later kit version with the rest of the board unaffected.
- The link test is defined once: a path is linkable if it is a Windows drive path, a UNC path, or starts with /Users/ or /Volumes/. The board, the aggregator and explain.py all apply that same definition.
- Local file paths: Copy path works for every row and needs no setup. Click-to-open needs a link handler on the user's computer (the optional local-files extra, Windows-only in this version); without one, use Copy path. On macOS there is no handler in this version, so Copy path is the route there even though macOS paths pass the row eligibility test in this same rule. A row is eligible when its path is a Windows drive path, a UNC path, or a macOS path under /Users/ or /Volumes/, or a web link; other paths, including workspace and sandbox paths, stay in the log only. The rules dialog says exactly this, in the same words.
