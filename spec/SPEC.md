# MyCommandCenter Board Specification

Version: current kit version (see the VERSION file at the kit root)
For: the Muse AI that builds and maintains this board, in the user's own Muse environment.

Build a private, fullstack web app (artifact) named MyCommandCenter (the user may choose a different display name during the interview; the internal name stays MyCommandCenter). The app stores its own data in the user's Muse environment. It is never published, shared, or exported. All data belongs to the user.

## 1. Layout

- Far-left vertical rail: the to-do list, headed "To-do's" (Section 2).
- Panel grid to the right of the rail (Section 3). On wide screens (1040px and up) the panels area has its own vertical scrollbar, capped to the viewport height, scrolling independently of the rail. Stacked phone layouts do not.
- The board's top header bar (the strip with the date and the COACH band) carries, at its right end, a desktop-only rail hide/show button (Section 2.2), the status-dot legend control, a New Panel button, a Collapse all / Expand all toggle (Section 3.6), and the Settings cog (Section 9), last in that order. The panels heading itself carries only its titles. There is no freshness or "Updated" text anywhere on the board. At narrow widths the header bar stacks and the COACH text truncates before any control is squeezed.
- Dark theme by default. All panel headers use a uniform slate charcoal fill #1c232e over a panel body fill #101216, including the recurring and links panels. The user may change the theme at any time; a theme change never touches data, and theme-dependent values in this spec are tokens, not fixed colors, where the spec says so.
- Fold controls everywhere are triangles: expanded ▼, collapsed ▶. This covers panel headers, the Done log fold, the weekly-audit fold, and the rail Expand/Collapse button (whose wording and size are unchanged). Add ("+") buttons, the Select-mode button, link icons, and × close buttons are not triangles.
- The COACH band at the top of the board: a label reading "COACH" beside a rotating set of short aphorisms. The set is stored on the board (Section 6) and the user owns it: they can replace the whole set during the install interview or at any later time by asking Muse, who writes the new set through the coach actions. Behaviour:
  - Fixed order. The band advances to the next aphorism every 5 minutes and once on each fresh page load. The current position is stored and remembered across loads, so the rotation continues where it left off instead of restarting. When no position is remembered (a fresh board, or the stored position cleared), the starting aphorism is chosen uniformly at random from the set.
  - Double-clicking the aphorism text, or double-clicking the "COACH" label, advances to the next aphorism at once, stores the new position, and restarts the 5-minute timer. The control carries the tooltip "Double-click for the next aphorism". On touch screens a double-tap does the same.
  - Each aphorism renders on exactly two lines. A two-sentence aphorism puts one sentence on each line. A single-sentence aphorism splits at a balanced point so the two lines are near equal. Wrapping never leaves a single orphaned word alone on a line. On phone widths only, if the two-sentence split would need a third line, the second sentence instead starts on the same line as the first and flows, so the aphorism still fits two lines; wider layouts always keep the sentence split.
  - The COACH label and the aphorism are each centered in the band independently. The band's height is held at phone and desktop widths.
  - The starter set below ships with the kit and is seeded at build (Section 8), unless the user replaces it in the interview. In this list, " / " marks the two-line split, and the first sentence of each two-sentence aphorism ends with an ellipsis:
    1. Protect the top three... / Finish one before opening another.
    2. Imperfect action beats / perfect planning.
    3. If everything is a priority, nothing is... / Pick three and defend them.
    4. Start small, finish completely... / Half-done is not done.
    5. Say no early... / A slow yes costs more than a fast no.
    6. Momentum beats motivation... / Move first, feel ready later.
    7. One front at a time... / Depth wins, breadth scatters.
    8. Decide once... / Reopening settled questions is work that produces nothing.
    9. Protect the morning... / The day is won or lost before noon.
    10. Done is a strategy... / Ship it, learn, adjust.
    11. Attention is the budget... / Spend it where it compounds.
    12. Write it down... / What is not captured is quietly forgotten.
    13. Review the week... / What gets reviewed gets better.
    14. Rest is part of the work... / A tired mind makes expensive mistakes.
    15. Prepare tonight... / Tomorrow is won the night before.
    16. Remove one friction... / Small drags sink big plans.
    17. Ask early... / A small question now beats a rescue later.
    18. Get clear first... / Ten minutes of clarity saves hours of wandering.
    19. Do it right once... / Rework is the costliest work of all.
    20. Play the long game... / Small wins, stacked daily, compound.
- Weekly audit entries can be saved: date, wins, stalls, next week focus. Keep all entries, newest first. In the recurring panel, the weekly audit sits at the top of the panel as panel-level furniture: it is not an entry, and it is not draggable.
- Responsive bands: 1040px and up, rail 300px. 820 to 1039px, two-column layout with a 272px rail that is sticky, height-capped, and internally scrolling, and the expanded to-do drawer offset to left: 272px. Under 820px, stacked layout; the rail's collapsed list keeps its height cap, and its expanded list grows to show five To-do's with exactly half of the first collapsed workstream panel visible below it as the scroll cue (Section 2.2).

## 2. To-do's (the Priority Rail)

The rail's heading is "To-do's". (Older drafts called the items "next actions"; that name is retired.)

### 2.1 Task record
Fields, with hard limits a build must enforce:
- title: string, required, 1 to 240 characters
- detail: string or null, max 600 characters (shown as Context in the drawer)
- due_date: string YYYY-MM-DD or null. Must be a real calendar date.
- estimate: one of 5m, 15m, 30m, 1h, 2h, 4hr, 6hr, 8hr, 10hr, 12hr, 12+hr, or null
- notes: string or null, max 5000 characters
- category: string or null. Preset suggestions come from the user's own taxonomy table (Section 2.8); free text is always accepted, whether or not the value is in the table.
- sub_category: string or null. Preset suggestions are the subcategories listed under the task's category in the user's taxonomy table (Section 2.8); free text is always accepted. Category and SubCategory are distinct fields; never merge them.
- waiting_on: string or null, max 5000 characters (the Waiting on / Blocked by column, Section 2.3)
- project_area: string or null, max 240 characters (free-form area label; the Bridge protocol writes this field)
- priority_tag: none, Important, or Critical. Labels only: no numeric priority exists anywhere in this design, deliberately. The manual order is the numbering.
- rank: positive integer, unique among open tasks. This is the saved manual order.
- status: open or done
- completed_at: timestamp or null
- created and updated timestamps (created drives the date-added sorts)

### 2.2 Rail presentation and the compact view
- Three columns: row number, the stacked Done/Delete button cell (Section 2.6), action name.
- A collapsed row shows the title, a priority-tag pill if tagged (Section 2.5), and, if set, the due date.
- Clicking a task name in the compact rail opens the expanded To-do's scrolled to that row, with a gold highlight on the row that clears when the drawer closes.
- Completing a task from the compact rail uses the same pre-completion confirmation as the expanded view (Section 2.6); nothing is saved before the user confirms.
- The add-task form on the rail has a functional Cancel button immediately left of "Add task": it discards the input, closes the form, and saves nothing.
- Rail hide/show: a button in the top header bar, immediately left of the status-dot legend, reads "Hide TO-DO's Rail" while the rail is shown and "Show TO-DO's Rail" while it is hidden. It toggles only the Priority Rail: the rail stays mounted, so its scroll position, an open drawer, and any search state survive; while the rail is hidden the panels take the full width and the expanded drawer re-anchors to the left edge. The toggle is view-only and resets to shown on reload. It is desktop-only: it is not rendered below 820px.
- Phone (under 820px): double-clicking the "To-do's" heading toggles the rail's list when the drawer is closed; when the drawer is open, it closes the drawer and lands on the collapsed rail. Collapse all panels also collapses the rail's vertical list, on phone only. With the rail's list expanded, the rail grows so five To-do's show at once and exactly half of the first workstream panel (collapsed) is visible at the bottom of the viewport as the scroll cue; collapsing the rail restores the capped layout.
- Rail header: a kicker line above the "To-do's" title reads "PRIORITY RAIL", and the live counts ("N open · M due ≤ 7d", the numbers in gold) sit at the right end of that kicker line. The "PRIORITY RAIL" kicker and the panels area's "OPERATIONAL PICTURE" kicker render at 11px, a scoped exception: the shared kicker size stays 10px everywhere else, including the drawer's "PRIORITY TABLE" kicker.

### 2.3 The expanded drawer
- A toggle opens an overlay drawer listing every open task with editable fields. A section kicker above the table reads "PRIORITY TABLE". Everyday columns shown by default: Name, Due Date, Date Added, Priority Tag, Context, Notes, Waiting on / Blocked by, Category, SubCategory, Estimate. A "NAME" column header sits above the task names, styled like the other column headers and centered across the name column. The Priority Tag column sits between Due Date and Context and is narrow: sized to its header (with its filter funnel) and the widest tag pill, no wider. All fields are inline editable and save in place.
- DATE ADDED column: read-only, immediately after DUE DATE, 88px wide. It shows the task's creation date as mm/dd/yy, vertically centered in the same shared 42px display box as the Due Date cell, at weight 400. Its funnel offers age buckets: This week (the current Monday to Sunday week), This month (the current calendar month), Older than 30 days, Older than 60 days, Older than 90 days ("older than N" means an age strictly over N days). A task can belong to several buckets; checked buckets union within the column and AND with the other filters and the search. The displayed mm/dd/yy text joins the displayed-text search.
- Waiting on / Blocked by column: immediately after Notes, at the Name column's width. It edits the task's waiting_on field inline, exactly like Notes (wrapping text, 5,000 characters). While editing, two small buttons above the editor, "Waiting on" and "Blocked by", insert that prefix ("Waiting on: " or "Blocked by: ") at the start of the text and park the cursor after it; clicking one while the other prefix is present swaps it, and clicking the one already present changes nothing. The prefix is never required and never validated; the field stores plain text, prefix included. The column carries the standard funnel (distinct values with counts, including (blank), alphabetical) and is covered by the table search.
- Rank handle: the drawer's rank cell box is 42px wide within its existing 46px grid track, so positions up to 999 render fully inside it. (The compact rail's rank span is a separate, known cosmetic overflow on 3-digit positions; see the CHANGELOG's known limitations.)
- NAME column search: a magnifier control ("Search by Name") sits immediately after the NAME label, with a one-letter gap. It opens a "Name contains" pane (light treatment, Section 3.6) with a text field; entered text filters rows by Name substring, case-insensitive, as a true column filter: it ANDs with the funnels and the global search, counts as an active filter (drag pauses while it is on), and clears when the field is emptied, when all filters are cleared, or when the drawer closes. A gold go-arrow button beside the field, or Enter, applies and closes the pane; the field's own clear control empties it; the pane has no Clear button of its own. While the filter holds text, every occurrence of the matched text in each visible row's Name cell is highlighted in gold; when the global search also runs, the Name cell highlights both phrases (deduplicated when identical) and other cells highlight only the global phrase. Layering: the heading text and the NAME label and its control sit above the filtered-column shade (Section 2.6), and the shade never intercepts the pointer.
- Action Name titles wrap to 3 lines at the unchanged column width; ellipsis only beyond 3 lines.
- While editing, the Action Name cell widens to 40ch + 16px with an opaque fill and shadow, the caret anchored at position 0; it returns to column width on save or cancel.
- Editor heights: the Notes editor opens at max(10 rows, which is 184px, the row's full current height). The Context editor opens at max(5 rows, which is 99px, the row's full current height). The taller-row rule wins in both, and any generic editor height cap is lifted for these two cells only. Other cells are unchanged.
- Escape layering in the drawer: while an inline editor is open, Escape cancels the edit (restoring the value from when the edit opened) and closes only the editor; it never closes the drawer, and the drawer's scroll and filter state are untouched. With no editor open, Escape closes the drawer. An open modal takes precedence over both: its Escape aborts the modal only.
- Due Date editing: clicking a Due Date cell always opens the calendar picker; no calendar icon is shown anywhere in the cell, in view or edit mode (the column's filter funnel is a separate control and stays). With the calendar open, Enter captures the currently chosen date (a valid typed value if typed, otherwise the highlighted day) and closes the calendar, saving the date; a Select button centered at the bottom of the calendar, between Clear (left) and Today (right), does the same on click. Clear and Today keep their behavior. Escape cancels without saving, per the layering rule above. The cell still displays the date as mm/dd/yy. In the drawer, the Due Date text is not bold and is set a half point larger than the drawer's standard cell text, in the cell and in the editor input alike.
- The Category and SubCategory cells are combo boxes: a preset dropdown fed by the user's taxonomy table (Section 2.8), SubCategory presets following the category on that row, plus free-text entry in both. A control in the drawer opens the taxonomy editor (Section 2.8).
- The drawer's Expand/Collapse symbol and the circular "+" are drawn and centered, level with their text label.
- To-do's have no link capability anywhere: no URL field exists on a task, in the drawer, or in the brief Add to To-do's modal. URLs inside notes or brief text are never auto-linked.

- Whichever arrangement is selected (My order, Batch, or a Sort view), a short description of it shows in the compact rail's sort bar in the same place and style: what the arrangement is, that Batch and Sort views are view-only and leave My order unchanged, and for My order the description reads: "My order: your own ranking. Drag to reorder or double-click the handle and type a position number. DEFAULT: new tasks join at the bottom. Tasks due-soon float to the top (see Settings). [Sort views] and [Batch] are view-only (no dragging)." The expanded To-do's shows no arrangement description; the rail's text is the only copy. The expanded To-do's header carries an X close control at its far right (on phone widths that fixed X is the drawer's only close control; the search bar carries none), and the taxonomy editor is opened from an "Edit categories" clickable text in the table header section at the Category column, not from a button in the drawer's top bar.
- Reordering in My order has exactly two methods: drag, and renumbering. Double-clicking a task's reorder handle (the grip and position number at the left of its row) turns it into an editable number field prefilled with the current position; typing an integer and committing moves the task to that position and shifts the others; a number past the end places it last and its displayed number becomes the true count; a number below 1 places it first; Escape or empty or non-numeric input cancels with no change. There is no arrow-key reordering. Both methods work only in My order and pause while the expanded To-do's column filters are active.
- Due Date sorting in the drawer: a paired-arrows sort icon button in the Due Date header's control cluster cycles a drawer-local sort: off, then ascending, then descending, then off. The DUE DATE header label itself is plain text and is never a sort control. The sort applies after the column filters and search, inside the visible set, using the same date comparators as the rail's Due views; undated tasks sort last in both directions, and ties keep the current rank order. Batch grouping is kept, with the sort applied within each group. While the sort is active, drag reordering and handle renumbering pause. The icon shows its state: both arrows muted when off, the up arrow lit in the accent color when ascending, the down arrow lit when descending, with state-aware accessible labels and tooltips. The sort resets to off when the drawer closes, together with the filters. No other drawer column is sortable.

### 2.4 Ordering: My order, sort views, Batch

- The saved manual order (rank) is sovereign. It is displayed by the "My order" view, which is the only drag-enabled view: dragging in My order, and only there, rewrites rank.
- View controls: a "My order" button and one dropdown. The My order button returns to the manual order and is lit while it is active; the drawer opens in My order, and choosing My order while already in My order changes nothing. The dropdown's first entry is Batch; its remaining entries are the eleven view-only sorts: Due soonest; Due latest; Title A–Z; Title Z–A; Category; Waiting On; Priority tag: Critical first; Estimate shortest; Estimate longest; Date added oldest; Date added newest. Selecting Batch turns Batch on and returns the ordering to My order; selecting a sort turns Batch off. The dropdown shows Batch while Batch is on, the sort's name while a sort is active, and the neutral placeholder "Sort view…" in My order. Items with no due date or no estimate sort last in those views. In every sort view, ties break by due date, oldest first, with undated tasks last; manual rank breaks any tie that remains. The My order view is exempt: it is the manual order itself, unchanged. Date-added sorts use the creation timestamp.
- A sort view never rewrites the saved order. The only way to adopt a displayed order is the separate "Make this my order" button, which asks for confirmation and then writes the full displayed order to rank.
- "Batch" (the dropdown's first entry): groups tasks into sections by Category/SubCategory, sections alphabetical A–Z, the blank batch (no category) last. Inside each batch, tasks keep My order. The due-soon float (Section 2.5) still applies ahead of grouping. In Batch view, all text in the rail and in the drawer renders in the board's gold, and the "BATCH" label renders faded. Adopting an order from Batch writes the full flattened displayed order, with confirmation, like any "Make this my order".
- Compatibility note: the due-soon float is a view behaviour of the board, not a change to saved order.

### 2.5 Due-soon float and priority tags
- The due-soon window is a board setting, "Due-soon window for To-do's" (Settings, Section 9), stored in days with a default of 3. It governs two things together: the float below and the yellow due-date pill tier. Changing it changes both.
- In every view, tasks due within the due-soon window are surfaced ahead, in chronological due date order, before the view's own ordering takes over for the rest.
- priority_tag renders as a filled pill beside the title: red #b23a26 with white text for Critical, gold #d4a72c with near-black text for Important. These are the same two tiers and colors as the recurring cue pills (ROUTINE-CATALOG.md); both meet WCAG AA against the panel fill.
- Tags never reorder the saved manual order on their own. They affect only the dedicated sort view and search.
- Due-date and Priority Tag pills share one standard box: padding 1px 7px, a 1px border, pill radius, 14px line height. On the rail, both pills share one width of 88px with the text centered. In the drawer, Due Date pills are 48px wide and Priority Tag pills are 76px wide; at phone widths the drawer's date pill sits flush to its column's left edge. Every Priority Tag and Due Date pill in this system renders its text at weight 400 on every surface. A Priority Tag pill's text size equals the Due Date pill's text size on the same surface: 10px on the rail, and the drawer's standard date text size (11.6667px) in the drawer. On the rail, a due date pill's vertical padding is split 2px top and 0 bottom (the pill stays 18px tall), which centers its text; tag pills keep the shared padding.
- Due-date pill tiers, one rule on the rail and in the drawer: PAST DUE (before today) renders as a filled red pill with white text. WITHIN THE WINDOW (today through the last day of the due-soon window) renders as a filled yellow pill with black text. BEYOND THE WINDOW renders with a white outline and no fill. Priority Tag refinements: the white outline on a beyond-window date appears only when the task's Priority Tag is Important; an overdue date on an untagged task renders instead as a white fill with red text; an overdue date on an Important or Critical task keeps the red fill with white text; the yellow within-window pill is the same for every tag. Panel item due dates use the same three tiers, without the Priority Tag refinements. "Today" is reckoned in the local time zone of the device viewing the board; there is no stored setting and no install question for it. The float above, the 7-day header count, and the drawer filter buckets all use that same "today", so they can never disagree. The drawer filter buckets and the Batch due-date groupings keep their fixed day boundaries and do not follow the due-soon window setting.

### 2.6 Drawer search and the Done confirmation

- The drawer search searches every field of every open task: Name, Due Date, Date Added, Context, Notes, Category/SubCategory, Waiting on / Blocked by, Estimate, Priority Tag. Case-insensitive. Multiple words are treated as one exact phrase. In the expanded drawer the search filters the table: a row with no visible hit is removed from the display while the search is active. The matcher searches the text as displayed, so a Due Date matches only in the mm/dd form the drawer shows and a Date Added only in its mm/dd/yy form. The compact rail is never filtered by search: it highlights matches in place and keeps every row.
- It shows a live match count and clears on Escape. A clear control (an ×) sits inside the search field at its right edge and appears only while the field has text; clicking it empties the search. There is no separate Clear button and no name-only scope option: the search always covers all displayed text.
- While a search is active, every occurrence of the phrase is highlighted in gold in the displayed fields (display-only; an open editor shows plain text), and "Make this my order" is disabled, so a filtered subset can never become the saved order.
- The search field flexes up to a 490px maximum width on phone widths and exactly 245px on desktop. Its label reads "SEARCH". The field's placeholder reads exactly "Enter text to search in whole table".
- Column filters: Due Date, Date Added, Category, SubCategory, Priority Tag, and Waiting on / Blocked by carry Excel-style funnels (the NAME column carries the Name contains filter instead, Section 2.3). Value funnels list the distinct values across all open tasks with counts and a (blank) entry, with Select all and Deselect all buttons and no Clear filter button; the Due Date funnel offers buckets instead (Overdue, Due today, Next 7 days including Due today, Later, No date). Filters AND with each other and with the search; sorts apply inside the filtered set; Batch groups only the survivors; "Make this my order" is disabled and drag is paused while any filter is active; filters reset when the drawer closes. A filtered column is signaled in its header only: the header label turns gold and the header cell carries a gold shade and a 3px gold underline, and that fill extends upward from the header into the heading strip as a per-column strip that starts below the "PRIORITY TABLE" kicker text, so the kicker itself is never shaded. There is no filter band and no badge anywhere. A "Clear all filters" control sits in the search row immediately to the right of the task count: subdued and inert when no filter is active, gold and clickable when any is; it clears every column filter including the Name contains text, and it also shows in the zero-result state, which reads exactly "No tasks match the current filters." Every funnel dropdown uses the light treatment (Section 3.6), with its Done button 28px tall, content width, centered. The compact rail keeps its own note, "Drag reorder is paused while column filters are active", while any filter is on; the drawer carries no such note.
- Done confirmation: pressing the Done circle in the compact rail or the expanded view opens a confirmation BEFORE anything is saved. It names the task, asks to mark it done, notes it can be undone in the Done Log of the Priority Rail, and offers Cancel and a confirm button; Escape and backdrop clicks abort like Cancel. Only the confirm completes the task; aborting changes nothing, and there is no post-save notice after a completion. (This confirmation replaces an earlier post-save notice design; do not build the notice.)
- Done and Delete controls, both views: in the compact rail and the expanded drawer, each open task has one cell with two controls stacked vertically, Done on top and Delete below. Done is a circle with a light green perimeter, the same size and style family as the rail's circle button. Delete is a trashcan icon, gray at rest, that turns red on mouse hover, with no circle or ring around it. Both carry Done and Delete tooltips. There is no separate Delete column in the drawer. The Done log keeps its own per-entry Undo and Delete controls, unchanged.
- Completing a task sets status done and completed_at, and moves it to the Done log view, timestamped, with undo. Undo restores it as open with its prior rank.
- Delete is offered per task in the compact rail and the expanded view (the trashcan control in the stacked cell), and per entry in the Done log (completed tasks can be deleted too). Deleting a task is a hard delete: the task is removed permanently, there is no Trash and no restore, and a deleted task never counts as completed. One task at a time; there is no bulk or multi-select delete for tasks.
- The delete confirmation shows the task's title, its Category, its SubCategory, and its due date (if any), and states that the deletion is permanent. Nothing is deleted before the user confirms; the user's click plus that confirmation is the explicit OK, and Muse never deletes a task on its own (OPERATING-RULES.md).
- Every deletion is recorded in a deletion log in board-owned storage: the deletion timestamp plus a full snapshot of the deleted task's fields. getdashboard returns the log, and the Done log view shows it as a read-only Deleted list (title and deletion timestamp, no restore or undo control). The log is append-only; no control edits or removes its entries. Deleting a task never touches panel items, other tasks, or the taxonomy table.
- A task is never completed, deleted, or given a due date or estimate by Muse on its own. See OPERATING-RULES.md.

### 2.7 Drag model (applies to rail tasks, panel items, recurring entries, and panels)

One drag model everywhere; do not implement variants.
- During a drag, the dragged element and all others stay put. There is no live reordering on pointer move. Live reordering teleports the dragged element under the pointer and caps movement at one position per drag; that behaviour is a known bug, never reproduce it.
- Midpoint geometry decides the landing slot. A gold line shows in the gap where the element will land. Edge auto-scroll works while dragging.
- The new order is committed once, on drop, and must allow a move of any distance in a single drag.
- Keyboard reordering with arrow keys is supported wherever dragging is (Section 3.3 for panels).
- Hovering any drag handle (panel grip, entry grip, rail grip) shows the plain default arrow cursor, never a grab-hand cursor, in rest, hover, and pressed states. A subtle hover background tint on handles is fine.

### 2.8 The Category/SubCategory taxonomy table

The preset lists behind the Category and SubCategory dropdowns live in board-owned storage, not in board code, so the user can change them without a rebuild.

Storage and shape:
- One taxonomy table per board, stored durably with the board's own data: an ordered list of categories, each carrying an ordered list of subcategories. A category entry is a name plus its subcategory names. Names are trimmed, non-empty strings of at most 240 characters, matching the task fields they feed.
- Category names are unique in the table. Subcategory names are unique within their category; the same subcategory name may appear under different categories, and subcategory presets are always scoped to their category.
- The kit ships this table empty. No categories or subcategories are ever shipped, seeded from an example, or copied from any other user's board. The setup interview collects the user's own categories, and the subcategories for each, and a setup step writes those answers into the table at install (INTERVIEW.md; prompts/01-install-core.md; prompts/03-email-brief-setup.md).
- getdashboard returns the table as a top-level taxonomy field, so a backup taken from getdashboard (prompts/upgrade.md) includes the table verbatim. Dedicated actions also read and modify it (Section 6).

One source, two consumers:
- The table is the single source for Category and SubCategory presets: the expanded drawer's combo boxes read it, and the Email Brief's category and sub_category suggestions read the same list (EMAIL-BRIEF.md sections 2 and 4). There is no separate brief-only category list; brief suggestions are read from the table at run time. If brief instructions record a copy of the list, it is a mirror only, recorded from the table at setup and refreshed by Muse whenever it changes the table, and the table wins on any disagreement.
- Changing the table changes only future preset suggestions. It never rewrites a stored task value by itself (see the rename and remove rules below).

The editor:
- A small editor, opened from a control in the expanded To-do's area, lists the categories and, under each, its subcategories, and lets the user add, rename, and remove categories and subcategories. New entries are added at the end of their list.
- The editor is buffered: adds, renames, and removes are staged locally while the editor is open and nothing is written until the user presses Save, which applies the staged changes through the taxonomy actions in Section 6 and reads the table back afterward. An Expand all / Collapse all button sits at the editor's top right, stacked directly below the corner X beside the title block; its label switches with state, it carries a triangle indicator, and it drives the same expanded state as each category row's own arrow. Cancel discards the staged changes and is never disabled; any attempt to close the editor with unsaved changes, by the corner X, Cancel, Escape, or a backdrop click, asks first, with the warning headed "Changes will be lost" offering Save changes and Discard changes (the unified dialog convention, Section 3.6).
- The editor dialog is a flex column: the category list scrolls inside it and the footer (Save, Cancel) stays pinned and visible at the bottom, however long the list grows.
- Save is partial, not atomic, and the spec says so plainly: the staged operations are applied one at a time, in order, and if one fails, the ones before it stay saved, the failing one and everything after it stay staged in the still-open editor, and the user is shown the error together with how many changes did save. There is no rollback.
- The rename count can drift, also plainly: the task count shown in a rename confirmation (Rename safety, below) is counted when the change is staged and is frozen at that number. If tasks are added, edited, or completed in the meantime, the number actually rewritten at Save can differ from the number the user confirmed, and nothing re-checks or warns at Save time.
- Add: adding a category or a subcategory touches no task. A name already present at the same level (in the same category, for a subcategory) is refused with a plain message.

Rename safety:
- On a rename, when the rename is staged (before Save is pressed), the editor counts the tasks carrying the old value and shows the old value, the new value, and that count, then offers two choices: update those tasks to the new value, or keep those tasks as they are. Nothing is rewritten without the user's explicit confirmation of one of those choices. The count is the staging-time count described above; it is not recounted at Save.
- Subcategory renames are scoped to their category: only tasks whose category is that category and whose sub_category is the old value are counted and, if the user chooses update, rewritten.
- If the user keeps the tasks as they are, those tasks keep the old value as free text (see the free-text rule below) and the table carries only the new value.
- The task rewrites, when chosen, go through the normal task update path, one task at a time, and change only the renamed field.

Remove safety:
- Removing a value never deletes, completes, or hides a task.
- If tasks carry the value being removed, the editor says how many, asks for confirmation, and offers two choices: reassign those tasks to another value at the same level (another category, or another subcategory in the same category), applied through the normal task update path, or leave the tasks carrying the removed value as free text.
- Removing a category also removes its subcategory list from the table. It does not touch the tasks' stored category or sub_category text beyond a reassignment the user explicitly chose, and a removed category's subcategory presets simply stop being offered.

Free-text rule (unchanged by the table):
- Category and SubCategory accept any typed value, in the drawer, in the add-task form, and in the brief's Add to To-do's modal, whether or not the value is in the table.
- A value that is not in the table displays and edits normally everywhere: the drawer, the column filters, Batch grouping, and search. It simply gets no presets: a task whose category is not in the table shows no SubCategory presets, and its SubCategory stays free text.
- An empty table is a valid state, for a new board or a user who never gave categories. In that state every Category and SubCategory is free text and nothing is blocked.

## 3. Panels

### 3.1 Panel record
- title: string, required
- kind: routine, standard, or links
- position: integer ordering within its column
- column: integer column index, stored explicitly (Section 3.2)
- collapsed: boolean
- item_sort: the panel's chosen item sort, one of az, newest, oldest, manual (Section 3.6). Defaults to az.
- items: list of panel items
- links: list of panel links (standard panels may carry links; the links kind is links only)

### 3.2 Panel layout: stored columns
- Layout is stored, not auto-packed. Each panel carries an explicit column index and a position within that column. Columns may hold different numbers of panels and stay that way across reloads.
- Dropping a panel into a column shifts only the panels below the drop slot in that column. No panel changes columns unless it is dragged there.
- The recurring panel is anchored: it sits at the top of the first column, and anything placed above it is normalized back to below it. Every other panel, including Quick Open, is movable like a standard panel.

### 3.3 Panel dragging
- Panels can be dragged only when all panels are collapsed.
- Blocked-drag modal: grabbing a panel grip while any panel is expanded opens a centered modal containing only the text "To drag a panel all panels will be collapsed first", with Proceed and Cancel buttons. Proceed collapses all panels and closes the modal, on success only (if the collapse fails, the modal stays open and shows the error). Cancel and Escape close it without collapsing. Backdrop clicks do nothing. There is no auto-dismiss timer. (An earlier design used a red banner here; do not build the banner.)
- Trigger-grip highlight: after that modal closes, the grip of the panel that triggered it stays highlighted (persistent gold accent, full opacity, not washed out by any blocked-state dimming). The highlight moves if a different panel triggers the modal, and clears when a drag of that panel finishes or is cancelled, when a keyboard reorder of it completes, or if the panel is deleted.
- Keyboard: Up and Down move within a column, Left and Right move across columns, under the same all-collapsed rule.
- Panel drag uses the Section 2.7 drag model: nothing moves during the drag, a gold line marks the landing gap, one commit on drop.

### 3.4 New-panel flow
- Creating a panel first shows a warning that creating it will collapse all panels; Cancel, Escape, and clicking outside create nothing and collapse nothing.
- On confirm, the new panel lands directly below the recurring panel, blinks gold until the user clicks anywhere on it, and a banner explains it can be dragged wherever they want.

### 3.5 Panel record details, deletion, selection

- Panel item record: title (required, max 240), detail, notes, due_date, status (free text), url (single link field, Section 7 surface 1), sort_order, item_type (Generic by default, or Project; standard panels only, Section 3.8), plus the recurring-only fields in Section 4. A Project item also carries its next actions in a child store (Section 3.8).
- Panel link record (link drawers): label (max 120 chars), destination (max 2048 chars), sort_order. See Section 7 for clickability rules.
- Panel deletion requires an empty panel, enforced by the board's data layer, not just the UI: zero items AND zero saved drawer links. The trash control on a non-empty panel opens a "Delete all items first" dialog showing the exact item and link counts. Once a panel is empty, a normal delete confirmation still applies. Both safeguards, always.
- System panels (recurring panel, File Saves History, Quick Open) cannot be deleted at all.
- Multi-select bulk delete, all non-recurring panels: each panel header has a Select toggle, rendered as a "−" icon button in the same format as the "+" add button; while selecting, that header button reads "Cancel". Checkboxes appear on items; a bulk bar offers, in this order: [Esc] [Select all] [Delete selected (N)], plus a hint. Delete asks for confirmation showing the count, then deletes exactly the selected items in that panel; item IDs from another panel must be refused. The recurring panel is the sole exception: no Select toggle. For File Saves History, the confirmation also states that deleted entries stay hidden and the files and master log are untouched (FILE-SAVE-LOG.md).
- Standard panel items can be reordered by drag (Section 2.7 model) and by keyboard.

### 3.6 Status dots, headers, editors

- Status dots: an item's dot reflects its free-text Status. Gold #d4a72c for build, active, or link. Gray #a6adb7 for open, blank, or unrecognized (the default). Red #d66c55 for blocked, waiting, due, or decision. Green #55a879 for routine or personal. Matching is by keyword in the status text. Never rewrite a user's stored Status values to make the dots behave; unknown values simply show gray. Hovering or focusing a dot shows a tooltip naming that item's own status: a recognized value reads "Status: link" (and likewise for the others); a blank status reads "Status: open (default)"; an unrecognized stored value reads "Status: <value> (unrecognized, shown as open)". Clicking a dot opens the same single status legend as the header-bar legend control; there is only ever one legend dialog.
- Legend: a single legend control in the board's top header bar shows only the four dots, no words, stacked in two rows of two. Its modal entries read "Status: ..." (one per meaning), and the modal's backdrop is fully transparent. The legend dismisses by its corner X under the dialog convention below, never by a footer button.
- Panel headers have two rows. Row 1 carries the grip, the panel name (a single line that never wraps, ellipsized if it is too long), the item count at the right end of the row, immediately left of the expand/collapse toggle, and the expand/collapse toggle at the extreme right. Row 2 carries the panel's sort dropdown at the left, under the title, and the link, delete, Select, and add controls at the right. A "Headers: 1 row / 2 rows" toggle in the panels heading governs row 2 for every panel at once: "1 row" hides row 2 everywhere, and "2 rows" shows row 2 even on collapsed panels. Panel collapse is a separate state: a collapsed panel shows only row 1 whatever the toggle says. Expand all and Collapse all return every header to the same uniform state.
- Panels open collapsed on every page load: on load, every workstream panel collapses to its title row, once per load, with no flash of a previous state. A panel the user expands during the session stays expanded until the next reload. The Priority Rail and the phone To-do's list are not affected.
- Per-panel item sort: every panel's header row 2 carries a sort dropdown with four options: A-Z, Newest, Oldest (Newest and Oldest by date added), and Manual. The default is A-Z on every panel. The choice is stored per panel (Section 3.1) and remembered across reloads. Sorting is view-only: it never rewrites the stored item order. Manual shows the stored order, and item drag-reorder works only while Manual is the panel's sort. On a collapsed panel the dropdown renders subdued (washed out); hover or keyboard focus restores it to full strength.
- White Edit window: the panel-item Edit window's fill is a theme token, --panel-complement (the complement of the panel fill; white #ffffff in the dark theme), with dark-on-light styling scoped to the editor only. The editor's footer save button reads "Save changes": it saves and closes. Dialogs and item rows keep the board theme. Never hard-code white; always use the token, so user themes keep working.
- Item editor polish (both the Generic and Project editors, Section 3.8): the TYPE / STATUS row aligns its four elements (the TYPE label, the Type dropdown, the STATUS label, the Status dropdown) by text baseline, so all four texts sit on one line; the gap between the Type dropdown and the STATUS label is 26px; the Status dropdown is 130px wide, sized to its longest selection. The editor's LINK field shows its placeholder ("https:// or C:\...") in plain gray #808080 with opacity 1; typed text renders in the field's normal dark color. The DETAIL field (the Project editor's OUTCOME / GOAL field shares the control) has a two-line minimum height and a ten-line maximum.
- Buffered saving in the panel-item editor: the editor (including the Email Brief entry's editor, EMAIL-BRIEF.md section 2b) stages its changes locally and writes nothing until Save changes, from every door that opens it. The per-entry control on an item row that opens this editor is labeled "Details". Cancel discards; closing with unsaved changes, by any path (the corner X, Cancel, Escape, or a backdrop click), asks first, with the same "Changes will be lost" warning (Save changes / Discard changes) as the taxonomy editor (Sections 2.8 and 3.6, dialog convention). Choosing Save changes in that warning applies the staged changes and closes the editor. Dirtiness counts only the fields the editor actually shows for that entry. Where a Save applies more than one action, it is partial in the same way as the taxonomy editor's: earlier actions stay saved if a later one fails, and the rest stay staged in the open editor with the error shown.
- Collapsed-panel add: clicking the add-entry "+" on a collapsed panel expands the panel and leaves the add form open and focused.
- Standard panel quick-add form: a "New entry name" label (gold, condensed, bold) sits above a full-width name field; below it, a centered controls row with a "Type:" label, the Generic / Project dropdown (Section 3.8), Cancel, and Add, all 24px tall and centered; below that, the hint "Choose Type [Project] if new entry has multiple action items", left-justified. The whole form sits in a bordered box in the panel header color. Enter is inert in the form. The dropdown, Cancel, and Add render in the same font as the name field; Add keeps inverted colors (gold fill, dark text). The name field starts at one row and grows to two when a name wraps. File Saves History's add row shows just the centered Cancel / Add row and no hint; the recurring and links panels keep their own add forms.
- Light treatment for new-entry panes: every new-entry pane uses the light treatment, the --panel-complement fill with dark-on-light styling: the rail's New task pane, the standard panel quick-add form, the Quick Open quick-add, the brief's Add to To-do's modal, the New Panel creation dialog, and the workstream link add form. The funnel dropdowns (Section 2.6) and the Name contains pane (Section 2.3) use the same light treatment. The panel-item Edit windows and the recurring type-picker form were already light and are unchanged.
- Standard action buttons: the shared form buttons and dialog buttons render 32px tall. Purpose-sized controls keep their own sizes and are not part of this rule: the brief bullet buttons (22px), the per-panel sort dropdown (19px), the funnel Done button (28px), and the quick-add controls row (24px).
- Collapsed-panel link icon: a panel's link icon toggles its Pertinent links drawer even while the panel is collapsed; the drawer renders directly beneath the header, with its usual contents and controls, and the panel itself stays collapsed. Every collapse-all path (the Collapse all toggle, the panel-reorder modal's collapse, creating a panel, and the opening boot collapse) also closes every open links drawer. Collapsing a single panel leaves its own drawer as it is, and Expand all does not close drawers.
- Workstream link add form: the NAME field opens truly blank, with no placeholder text, and opening the form clears any label or destination left from a previous entry. The DESTINATION field starts empty and shows its hint ("https://, onenote:, C:\..., or \\server\...") as a placeholder in plain gray #808080 with opacity 1; typed text renders in the field's normal dark color.
- Panel-narrow overflow: when a panel narrows, the panel-item editor's fields shrink below their minimum content width instead of overflowing the editor.
- Card name editing: a single click on a workstream card's name never enters rename or edit mode. On hover over the name, a small pencil icon appears at its edge, and clicking the pencil opens the name editor (on touch, tapping the name selects it and shows the pencil). The pencil is the only mouse path into name editing. The same rule applies to any item title inside a card that would otherwise enter edit mode on a single click.
- Double-clicking a card's header (its background or name, never a link, button, or other control in the header) toggles that card's expand/collapse, the same end state as its fold triangle. Double-click never opens an editor.
- Links-panel item editor: for an item on a links-kind panel (Quick Open), the panel-item editor shows neither a STATUS field nor a DUE field. Stored values are preserved exactly: an untouched save writes the loaded status and due date back unchanged. Routine-panel and standard-panel item editors keep their fields.
- Links-panel creation default: an item created on a links-kind panel is born with status "link" unless a status is explicitly supplied at creation, in which case the supplied value is stored exactly. Items created on every other panel kind are born "open". The default applies at creation only and never rewrites existing items.
- STATUS field in the standard panel-item editor: a dropdown, never free text. The options, in order (the stored value is the bare word; the display label capitalizes the status word only): open (gray), build (gold), active (gold), link (gold), blocked (red), routine (green), displayed as "Open (gray)", "Build (gold)", "Active (gold)", "Link (gold)", "Blocked (red)", "Routine (green)". Stored values stay lowercase. If the item's loaded status is outside that set, one extra option carries it as the initial selection, labeled "<value> (current, unrecognized)" for a nonblank value or "open (default)" for a blank one, and an untouched save writes the loaded status back byte-exact. Links-panel editors show no STATUS field at all (above); routine-panel entries show none in this editor either.
- Dialog convention (unified): every modal dialog carries a bare corner X at its top right, with no surrounding circle, no border, and a transparent background. A gold footer button still means a decision is present (Save, a confirmation, or an action with consequences). A dialog that only informs (the status legend, the File Save Log completion pop-up, the File Save Log rules dialog, the panel-not-empty notice) has no footer button and dismisses by its corner X, alongside whatever Escape and backdrop behavior it already has. On an editor dialog (the panel-item editor in all its forms, the Categories taxonomy editor, the routine entry editor), the corner X does exactly what the editor's Cancel button does, and the editor's footer Cancel is never disabled: with no unsaved changes, the X, Cancel, Escape, and a backdrop click each close the editor at once; with unsaved changes, every one of those paths shows the same warning, headed "Changes will be lost", offering "Save changes" and "Discard changes", and nothing is discarded until the user chooses Discard changes. On a confirmation dialog, the corner X counts as that dialog's cancel choice. The File Save Log guidance modal follows the same split: its only footer button is the consequential "Cancel update", and dismissal is the corner X. The File Save Log FILTER modal's only close control is its corner X: its header carries no Minimize or Close text buttons; the FILTER modal has no Escape or backdrop dismissal. Settings dismisses by its corner X and has no footer Close button.

### 3.8 Typed panel items: Project

Standard panel items carry a Type: Generic (the default) or Project. Recurring and links panels have no Type control. No panel ever defaults an entry to Project: the quick-add form's Type selector starts at Generic for every entry, remembers nothing, and resets after each add, and any standard panel holds Generic and Project entries mixed freely. A panel's name never implies a restriction on entry type.

- Project fields: Detail is labeled OUTCOME / GOAL. A target date is labeled TARGET COMPLETION and is Details only, never shown on a card. A NEXT ACTIONS list holds up to 10 actions; each action has text (300 characters), a DUE date, an OWNER (120 characters), and a BLOCKER / WAITING ON (300 characters). A new action's OWNER pre-fills from the previous action's owner. List order is priority order.
- NEXT ACTIONS starts collapsed on every editor open: only the section header and its toggle show; the toggle is always enabled, so a first action can be added from the collapsed state.
- Card rendering: a Project card adds at most two lines to the Generic rendering, each only when it carries data: a "Next: " line (the first action whose linked To-do is not done, with its due date in the tiered pill colors of Section 2.5 and a "+N more" count when further open actions follow) and a red "Stuck: " line (that action's blocker). Owner and Target completion never render on a card.
- Editor: the field order is NAME, TYPE and STATUS on one shared row, OUTCOME / GOAL, TARGET COMPLETION, NEXT ACTIONS, NOTES, LINK. NAME is a textarea that starts at one row and grows to two (Enter is inert in it). The Generic editor keeps the same shape: NAME, TYPE and STATUS, DETAIL, DUE DATE between DETAIL and NOTES, NOTES, LINK. In both editors the Type dropdown, the DETAIL / OUTCOME / GOAL field, and the DUE DATE / TARGET COMPLETION inputs render at 13px with a 1.4 line height, and the TYPE / STATUS row aligns its items by text baseline (Section 3.6 carries the row's spacing and dropdown sizes in the editor polish rules below).
- Switching an item from Project to Generic hides the Project fields and shows the warning "Project fields will be hidden, not deleted. They come back if this item becomes a Project again." Hidden values are kept in storage and are never cleared by a save.
- Statuses: Project items use the same six statuses as Generic items (Section 3.6).
- Linked To-dos: a next action reaches the To-do's only through its own "Add to To-do's" button in the editor, never automatically. The click saves the item first if it is dirty, then creates one task titled "<item> | <action>" with the action's due date and blank Category and SubCategory. The link is stored on the action row as the linked task's id; there is no source-key field and no source-key dedupe in this design. While an action is linked, its button reads "Added to To-do's" with a check and does nothing. Completion lives only on the task and reflects both ways: completing the task shows the action as done, and the editor's completion control completes the task through the board's normal Done path. Saving the item propagates action text and due-date edits to a linked open task, never the reverse. Editing a completed action's text unlinks it; the completed task stays in the Done log. A hard delete of the linked task re-arms the button. The editor's trash icon on an action deletes the linked To-do when one exists, and otherwise deletes the action row; its confirmation names the target.
- Bridge: Project fields and actions are preservation-only. getdashboard returns them; add-panel-item and update-panel-item requests cannot author them; an update that omits them leaves them untouched (BRIDGE-PROTOCOL.md). The board snapshot, where one is rendered, shows a Project item's Next and Stuck lines from its first open action.
- Storage: an item_type field on panel items (default Generic) and a next-actions store holding each Project item's action rows, each with its linked task id or none. Fresh installs create both; the seed creates no Project items.

## 4. Recurring panel behaviour

The full entry-type system is specified in ROUTINE-CATALOG.md. The data model here must support it:

- Each recurring entry carries a stored entry_type and a type config. Behaviour keys off the stored type and config, never the entry's title, so renaming an entry never strips its behaviour. (Title-matching behaviour is a known anti-pattern; never reproduce it.)
- Entry types: daily-check; weekday-check; sessions (multiple times a day); brief (carries long notes text and the brief reader, EMAIL-BRIEF.md); weekly-check (config: due weekday); monthly-check (config: due day 1 to 29, or the distinct stored value "last" meaning Last day of Month, resolved to each month's real final day; legacy stored 30 or 31 are read as "last"); interval-check (config: every N days).
- Sessions config: a list of sessions, each with a stable key, a label, and a time. Per-session completions are stored against the session key, not the label, so relabeling or retiming a session never erases that day's check. At least one session is required. Sessions display sorted by time, and are editable: add, remove, relabel, retime.
- Session chips: an entry's session chips render in one row at desktop card width: the gap between chips is 4px, and the gap between a chip's checkbox and its label is 3px. Labels stay at 10px, checkboxes at 16px, and the click area 28px tall. At the narrowest phone width the row may still wrap; the font never shrinks at any width.
- Session label display: a session label that is purely a time renders lowercase with no space ("10 AM" shows as "10am", "2 PM" as "2pm"). A label that is not a time renders exactly as stored. This is a render rule only: stored labels, session times, session keys, checkoffs, and the editor's display are unchanged.
- Recurring entry banding: entries in the recurring panel alternate fills; the alternate fill token, --routine-fill-alt, is #181c23 in the dark theme.
- Completions: daily and weekday entries carry a completed date; weekly entries a completed week; monthly entries a completed month; interval entries a last-completed date. An entry presents as due per its type's logic (ROUTINE-CATALOG.md).
- The recurring panel's "+" opens a type picker with the seven types. Other panels keep the simple title-only add.
- The shared add-entry form (the form the recurring panel's type picker leads into, and the add form on routine-kind panels) treats the name as required. The name field's label reads "Name *" with a red asterisk and the field is marked required; its placeholder reads exactly "Enter a name here for the new item". The Add entry button is disabled while the name is empty or whitespace only. Hovering the disabled button shows a tooltip above it reading "Enter a name before Adding" (italic black text on white); clicking the disabled button flashes the same tooltip for about 2.4 seconds; typing a name removes the tooltip. The name field itself keeps a white fill, with a bold gray placeholder (#808080) and black typed text. Every other data-entry input in the form carries the board's green entry treatment (a tint of the done green as fill, with a deepened green border), the same treatment as the Email Brief entry's TIME inputs; the name field is the one deliberate exception and keeps its white fill.
- Type picker fade: once a type is selected in the picker, every unselected option's title and description render washed-out gray; the options remain fully clickable, and selecting a different one moves the fade. (The entry editor's own type control, a plain select, is a different control and does not fade.) The picker cards' titles and descriptions render in near-black (--panel-complement-text) at rest, selected or not; the selected card keeps its gold border and tinted highlight.
- The recurring entry editor has no Status and no Due fields (standard-panel item editors keep both). An entry may still carry a stored status (shown by its dot); never strip stored values just because the editor no longer exposes the fields. In the entry editor, every session row's LABEL and TIME cells carry the board's light-green data-entry fill (the done green mixed toward white, with the deepened green border), the same fill as the Email Brief entry's TIME inputs and DAYS checkboxes (EMAIL-BRIEF.md section 2b).
- Per-entry links: a recurring entry supports a list of links (label plus destination, up to 20 per entry), editable in the entry's Edit window and rendered clickable on the entry (Section 7 surface 3). A single pre-existing link on an entry migrates in as the first list item.
- Recurring entries are draggable within the panel (grip, plus Up and Down keys), persisting sort order only, under the Section 2.7 drag model.
- One entry is reserved for Email Brief notes. It carries the dedicated routine type "Email briefs" (stored type email_briefs; created by the Email Brief setup); the generic "Brief / report" type is a different, ordinary type and never gets the Email Brief treatments. Its notes hold the rolling stack specified in EMAIL-BRIEF.md. For this entry only, its type config also carries a days array beside its sessions: the days briefs run on, chosen with seven day checkboxes in the entry's editor; when no days are stored the entry runs Monday to Friday (EMAIL-BRIEF.md section 2b).
- Board session times are board-only state. External reminder jobs created by a module setup are separate; changing board session times does not retime them (the setup prompts keep them in sync explicitly, or warn).

This is the only action that writes Email Brief session checkoffs: the brief checker never calls it, and the shared session-completion action above is never used for the Email Brief entry.
- setbriefflag (flag key, flagged boolean): sets or clears the persistent Flag on a brief bullet (EMAIL-BRIEF.md section 6). Flags live in their own store, keyed by the bullet's Open link when it has one, and otherwise by its bold lead together with the brief's date, never in the brief text.
- setbriefbulletminimized (bullet key, minimized boolean): sets or clears a brief bullet's minimized state (EMAIL-BRIEF.md section 6). The minimized state lives in its own store under the same bullet key as the Flag, never in the brief text, and is returned in the dashboard payload.
- acknowledgebriefheading (heading): records the acknowledged brief heading for the brief-arrival pop-up (EMAIL-BRIEF.md section 7). The dashboard payload also carries the pop-up publication record (the published heading, its landed stamp, and the acknowledged heading) and a content version of the Email Brief entry's notes, so an open board can notice a new or amended brief.

Storage additions in this version: the per-panel item_sort field (Section 3.1); the due-soon window setting (default 3 days); the user-only Email Brief session checkoff store; the brief flags store; the COACH aphorism set with its rotation position; the brief Minimize store; the brief pop-up publication record; and the Project item storage (the item_type field on panel items, default Generic, and the next-actions store, Section 3.8). Fresh installs create all of them at install time, empty or at their defaults. Upgrades add each one only where it is missing and never rewrite existing data to do so (prompts/upgrade.md). Two schema maximums also rise in this version, with no data rewrite: the panel-item notes maximum is 150,000 characters (the Email Brief stack cap, EMAIL-BRIEF.md), and the task waiting_on maximum is 5,000 characters (Section 2.1). Task source keys with server-side dedupe for the brief's Add to To-do's remain designed and gated, and are not part of this version.

Validation the build must enforce: required titles non-empty; due dates are real YYYY-MM-DD dates; estimates from the enum in 2.1; priority_tag only none, Important, or Critical; the taxonomy table follows the shape and uniqueness rules in Section 2.8, while task category and sub_category values themselves are never validated against the table (free text is always accepted); bulk delete refuses IDs outside the named panel; panel deletion refuses a non-empty panel (items or links) at the data layer; deletes of tasks, panels, and panel items execute only after the caller's confirmation step (the confirmation itself is a UI and Muse behaviour rule, OPERATING-RULES.md).

## 7. Link rules: three surfaces, kept separate

Conflating these surfaces causes real bugs. Spec and build them apart.

Surface 1, the single Link field (standard-panel and links-panel items): the destination is stored verbatim and rendered as a raw link. https works; a pre-formed custom-protocol URL works. A bare local path typed here is not converted and will not open properly; that is expected, do not "fix" stored values.

Surfaces 2 and 3, panel link drawers (multiple links per standard panel) and recurring-entry link lists: both are gated by one renderer rule. Clickable: http:// and https:// on any domain; onenote: links; file:// links; and local Windows paths (drive-letter or UNC), which are converted to the local-opener protocol of the optional local-files module (the opener URL is the protocol name plus the fully percent-encoded path; the module keeps its own allowlist of folders and blocks scripts and executables). Everything else (mailto:, tel:, ftp:, custom app schemes, ready-made opener URLs, relative paths, bare names) is stored and shown as plain text with a Copy control.

Server-side validation, surfaces 2 and 3 only: destination non-empty, label at most 120 characters, destination at most 2048 characters. Clickability is purely a rendering decision.

Preservation rules: never clean up, normalize, or re-encode a stored destination. Moving a link between surfaces changes its clickability, and that is correct behaviour, not data loss. (Many note-app links are in fact https URLs with an embedded app suffix and open as web pages; that is fine.)

File Saves History rows and Quick Open (Level 1): an expanded File Saves History row may offer an "Add to 'Quick Open'" action (FILE-SAVE-LOG.md section 4). The item it creates carries the file's path as copyable text in its Link field, not as a clickable local-opener link, because the kit ships no link handler; a user who later installs the optional local-files extra can replace the text with a working link by hand. It is born with status "link" under the links-panel creation default (Section 3.6).

## 8. Seed

Build the board empty of content: panels and routine entries from SEED.json for the chosen pack (routine entries seeded with their types), no tasks, no panel items with invented content, no links except any the user provides in the interview, and the COACH aphorism set: the starter set listed in Section 1, seeded from this spec at build, unless the user replaces it in the interview (INTERVIEW.md). The starter set is board content the user owns; it does not live in SEED.json, and replacing it never changes the seed format. The taxonomy table (Section 2.8) is created empty at build, exactly as the empty taxonomy list in SEED.json, and is populated only from the user's own interview answers. Demo data exists separately (seed/DEMO.json), carries no categories, and loads only if the user explicitly asks for it. The top-level "version" field inside SEED.json and DEMO.json (currently "0.1.5") is the seed format version: it changes only when the seed data format changes, and it is independent of the kit version.

## 9. Settings (the cog)

A cog icon at the top right of the board's header bar opens one Settings dialog. Its purpose is post-install change: anything the setup interview asked that the user may later want to adjust has a discoverable home here, so the interview may defer non-essential questions with an honest "you can change this later from the cog".

The governing rule is ONE editor per setting. The cog is a front door, never a second copy: every control in the dialog either edits a board-owned value through the same stored field its other door uses, or opens the existing editor component for that setting. No setting may have two writable homes, and the in-context doors (the drawer's "Edit categories", the Email Brief entry's own Details, the filter modal's Show count) keep working and reach the same single editors and values.

The dialog has three short sections:

- Board: a row labeled "Default Show count for File Saves History" (only when the File Save Log module is installed; it is the same stored value the filter modal's Show count uses, so a change in either place is the same change), a row labeled "Due-soon window for To-do's" that edits the due-soon window in days (default 3) through the same stored value the Priority Rail float and the yellow due-date pill use (Section 2.5), and a Categories and subcategories row that opens the taxonomy editor (Section 2.8), which remains the single taxonomy editor.
- Email Brief: a Brief times row that opens the same editor the Email Brief entry's own Details uses (the multi-session slot editor). No second slot editor exists.
- File Save Log (only when the module is installed): routing rows only, for settings that live on the user's own computer and that a hosted board cannot edit. Settings that live in local files (the scanner's watched folders and schedule in its config file, the hide and keep rules in the excludes user file) must never appear as live toggles. Each routing row follows one pattern, in the same gold-bordered callout style as the explainer's "Changing rules:" box: a one-line description of what it controls, a copyable plain-words request the user can send to Muse, and, for technical users, the generic config or file path.

When the File Save Log module is not installed, including every install where it was skipped (for example because the user's computer is a Mac; the module is Windows-only in this version), the dialog has only the Board and Email Brief sections, and the Board section omits the Default Show count row as well. That absence is correct, not missing structure.

Dialog behaviour: the dialog's header (its title and corner X) is a fixed row above a separately scrolling body: the body scrolls beneath it, the header never moves, and the scrollbar spans only the body. Escape closes the dialog and nothing else (the board's Escape layering rule applies); on close, focus returns to the cog; the cog and dialog are keyboard reachable; the dialog is usable at phone width (390px); styling follows the board theme. Opening an editor from Settings closes the Settings dialog first, so the dialog and an editor never stack.

Out of scope for the cog: anything that duplicates an existing editor in a second place, notification preferences, account or sharing settings, and any bridge or chat-side action that edits settings (read-only visibility at most).

## 10. What this spec deliberately omits

- No numeric priority (no P1/P2): the manual order is the numbering, and numbers would duplicate and contradict it.
- No Eisenhower quadrants, no energy levels: maintenance overhead, tested and rejected in the reference design.
- No hover grab cursors, no live-reorder dragging, no red blocked-drag banner: each was tried in the reference design and removed; Sections 2.7 and 3.3 carry the fixed behaviour.
- No email delete affordance anywhere, including in the Email Brief: held by explicit product decision. If it is ever revisited, it would be move-to-Trash only, per-message confirmation, and never bulk.
- No sharing, no public link, no multi-user editing: the board is private to its owner.
- No email sending, no external posting: the board records and reminds; acting outside is the user's.
